# ⚙️ Convertly Hub - SaaS File Converter & API Platform

Мікросервіс для швидкої конвертації файлів із наданням публічного API для розробників. Проєкт поєднує зручний користувацький інтерфейс і надійну серверну інфраструктуру обробки даних.

---

## 1. Вступ і цілі проєкту

**Назва проєкту (робоча):** Convertly Hub

**Основна суть продукту:**
Проєкт є вебзастосунком (SaaS-платформою), що надає послуги швидкої конвертації файлів між різними форматами. Взаємодія із сервісом відбувається двома шляхами: через графічний користувацький інтерфейс (B2C-сценарій для звичайних користувачів) і через публічне REST API (B2B/Developer-сценарій для інтеграції у сторонні програмні продукти).

**Основна мета:**
Розробка легковагого, але архітектурно масштабованого сервісу конвертації файлів, що містить повноцінну систему авторизації, керування профілем користувача, генерацію унікальних ключів доступу та надійне ядро (Core) для обробки медіафайлів і документів.

**Ключові завдання проєкту:**

1. **Реалізація Core-начинки.** Створення відмовостійкого механізму приймання, обробки та повернення файлів без критичного навантаження на основний сервер.
2. **Надання API.** Розробка захищеного ендпоїнта, що дасть змогу стороннім розробникам надсилати файли на конвертацію, використовуючи унікальний API-ключ.
3. **Керування станом користувача.** Створення особистого кабінету з гнучкими налаштуваннями приватності (можливістю вмикати/вимикати збереження сконвертованих файлів на сервері).
4. **Побудова UX/UI.** Розробка інтуїтивно зрозумілого інтерфейсу для ручного завантаження файлів із коректним зворотним зв'язком за будь-яких сценаріїв (успіх, помилка, перевищення ліміту).

## 2. Архітектура й технологічний стек

### 2.1. Концепція архітектури

Система будується за принципом розділення відповідальності (Separation of Concerns) і концептуально ділиться на три незалежні шари. Такий підхід забезпечує відмовостійкість, характерну для надійних корпоративних сервісів, і дає змогу масштабувати кожен компонент окремо:

- **Клієнтська частина (Frontend).** Вітрина сервісу й інтерактивний особистий кабінет користувача.
- **Серверна частина та API (Backend).** Обробка бізнес-логіки, автентифікація, маршрутизація й перевірка лімітів.
- **Core-рушій (Workers).** Ізольоване середовище для виконання ресурсомістких завдань перекодування файлів.

### 2.2. Основний фреймворк та інтерфейс

- **Фреймворк: Next.js (App Router).** Виступає головним оркестратором. Використовується для серверного рендерингу (SSR) інтерфейсу та створення захищених API-маршрутів.
- **Стилізація та UI: Tailwind CSS.** Гарантує створення строгих, легковагих і повторно використовуваних UI-компонентів без перевантаження клієнтської частини зайвими CSS-бібліотеками. Особливу увагу приділено візуальному зворотному зв'язку: мікровзаємодіям, станам Drag & Drop-зон та індикаторам прогресу.

### 2.3. Інфраструктура даних

- **Реляційна база даних.** PostgreSQL у зв'язці з Prisma ORM. Відповідає за надійне зберігання строго структурованих транзакційних даних: профілів користувачів, хешів паролів, згенерованих API-ключів і логів (історії) конвертацій. Самі файли в БД не зберігаються.
- **Об'єктне сховище.** S3-сумісне сховище (наприклад, MinIO або AWS S3). Забезпечує потокове завантаження (Streaming) і віддавання файлів. Використання незалежного сховища закладає архітектурний потенціал для горизонтального масштабування та керування великими обсягами медіаданих (аж до виділення терабайтних пулів для акаунта).

> **Уточнення щодо інфраструктури сховища:**
> Для MVP, захисту проєкту й навіть початкового запуску SaaS-продукту не доведеться платити за сховище на старті. Архітектура S3 стала стандартом (API), тому є кілька чудових безкоштовних варіантів реалізації:
>
> - **MinIO (локально для розробки).** Це S3-сумісне сховище, яке піднімається локально через Docker буквально однією командою. Воно не потребує інтернету та фінансових витрат. Ідеально для написання коду й тестування. Коли код працює з MinIO, він працюватиме з будь-яким іншим S3-сховищем без переписування логіки.
> - **Cloudflare R2 (для продакшену).** Безкоштовний тариф надає 10 ГБ сховища щомісяця та нульову вартість вихідного трафіку (egress fees). Для SaaS-конвертера, де користувачі постійно завантажують файли, це оптимальний вибір.
> - **AWS S3 Free Tier.** Amazon надає 5 ГБ безкоштовно на перші 12 місяців.
> - **Supabase Storage.** За використання Supabase як бази даних (PostgreSQL) платформа надає вбудоване S3-сховище (1 ГБ у безкоштовному тарифі).
>
> _Отже, проєкт Convertly Hub може бути повністю реалізований і запущений на базі безкоштовних потужностей._

### 2.4. Core-рушій та ізоляція процесів (розв'язання проблеми Event Loop)

Оскільки JavaScript є однопотоковою мовою, виконання складних математичних обчислень прямо на backend-сервері неминуче призведе до блокування Event Loop. Щоб «важкий» файл не зупинив роботу всього сервісу для інших клієнтів, застосовується роздільний підхід:

- **Синхронна обробка (легкі завдання).** Конвертація зображень (`JPG ↔ PNG`) виконується за допомогою високопродуктивної бібліотеки `sharp` (Node.js). Операція відбувається на рівні C++, триває мілісекунди та безпечно виконується в основному процесі.
- **Ізольована обробка (важкі завдання).** Конвертація документів (`DOCX → PDF`) делегується окремому мікросервісу (наприклад, `Gotenberg`, розгорнутому в ізольованому Docker-контейнері). Next.js тут виступає виключно як шлюз: приймає файл потоком, передає його мережею незалежному воркеру, очікує відповідь і повертає готовий PDF клієнту. Це гарантує безперебійну роботу основних API й UI навіть під піковим навантаженням.

## 3. Вибір форматів файлів і бізнес-логіка

### 3.1. Підтримувані формати (Scope для MVP)

У межах першої версії продукту реалізовано підтримку двох найбільш затребуваних напрямів конвертації, кожен з яких демонструє різні архітектурні підходи до обробки даних:

- **Зображення (JPG ↔ PNG).** Демонструє миттєву (синхронну) обробку легковагих медіафайлів. Виконується потоково, не потребує значних ресурсів і дає змогу протестувати пропускну здатність API за множинних запитів.
- **Документи (DOCX → PDF).** Демонструє асинхронну обробку та роботу Core-рушія з важкими форматами. Має високу комерційну цінність (B2B-сегмент) і доводить здатність архітектури не блокувати основний Event Loop сервера під час складних математичних операцій рендерингу шрифтів і розмітки.

### 3.2. Політика зберігання та керування приватністю (User Control)

Ядром бізнес-логіки платформи є строгий контроль користувача над своїми даними. Керування здійснюється через глобальний перемикач (Toggle) «Зберігати результати конвертації», розташований в особистому кабінеті.

Логіка роботи механізму:

- **Стан «Активно» (за замовчуванням).** Усі завантажені файли (як через вебінтерфейс, так і через публічне API) після успішної конвертації зберігаються в S3-сховищі. У базі даних створюється запис із метаданими файла, який миттєво відображається в таблиці файлового менеджера особистого кабінету користувача.
- **Стан «Вимкнено» (Privacy Mode).** Система переходить у режим обробки «на льоту» (In-Memory / Temp Storage). Сконвертований файл повертається клієнтові як бінарний потік або тимчасове захищене посилання (TTL 1 година) й негайно видаляється із серверів платформи.
- **Ізоляція станів (зворотна сумісність).** Переведення перемикача в неактивне положення впливає виключно на майбутні конвертації. Файли, які вже перебувають у профілі користувача, не зазнають автоматичного видалення й лишаються доступними для завантаження до моменту ручного видалення користувачем.

## 4. Структура сторінок і користувацькі сценарії (UI/UX)

### 4.1. Головна сторінка (Landing & Conversion Zone)

- **URL:** `/`
- **Призначення:** основна точка входу, що демонструє ключову цінність сервісу без обов'язкової реєстрації.
- **Структура блоків:** Hero-секція з описом і два Drag & Drop-віджети (зона завантаження зображень і зона завантаження документів). Індикатор прогресу конвертації та кнопка завантаження.

### 4.2. Блок авторизації (Auth Flow)

- **URL:** `/auth/login` и `/auth/register`
- **Призначення:** ідентифікація користувачів для доступу до функціональності особистого кабінету.
- **Структура блоків:** мінімалістичні форми з полями Email і Password, а також посиланнями на відновлення доступу.

### 4.3. Особистий кабінет (Dashboard & Profile Management)

- **URL:** `/dashboard` (доступно лише авторизованим користувачам)
- **Призначення:** центр керування акаунтом.
- **Структура блоків:**
  - **Керування профілем:** редагування особистих даних.
  - **Керування API-доступом:** блок із поточним API-ключем, кнопками копіювання та регенерації.
  - **Налаштування сховища:** перемикач «Зберігати сконвертовані файли у профілі».
  - **Файловий менеджер:** таблиця з історією транзакцій і посиланнями на завантаження збережених файлів.

### 4.4. Сторінка документації API

- **URL:** `/docs`
- **Призначення:** технічний посібник для сторонніх розробників з інтеграції конвертера.
- **Структура блоків:** опис ендпоїнтів, вимоги до автентифікації (Bearer-токен), снипети коду (cURL, JS) і таблиця розшифрування HTTP-помилок.

### 4.5. Панель адміністратора (Admin Panel)

- **URL:** прихований ендпоїнт (наприклад, `/system-manage/login` або `/portal-access`). Суворо виключений із файла `robots.txt` та карти сайту.
- **Призначення:** внутрішній інструмент для керування платформою й моніторингу її стану.
- **Структура блоків:**
  - **Дашборд метрик:** загальна кількість користувачів, кількість конвертацій за 24 години, навантаження на воркери.
  - **Керування користувачами:** пошук за Email, можливість примусового блокування акаунта (Banned) або ручного скидання пароля.
  - **Керування API-ключами:** можливість відкликання (Revoke) ключів, для яких зафіксовано аномальне навантаження або спам-активність.

## 5. Авторизація та керування доступом

### 5.1. Основний механізм автентифікації

Для забезпечення безпеки сесій і роботи публічного API використовується комбінований підхід:

- **Вебклієнт (особистий кабінет).** Автентифікація реалізується на базі бібліотеки `NextAuth.js` (`Auth.js`) із використанням захищених `HttpOnly` cookie. Це стандартний і найбезпечніший метод для Next.js-застосунків, що захищає токени сесії від XSS-атак (міжсайтового скриптингу).
- **Публічне API.** Автентифікація відбувається за статичним API-ключем (Bearer Token), який передається в заголовку запиту.

### 5.2. Політика зберігання облікових даних

- Платформа не зберігає паролі користувачів у відкритому вигляді. Під час реєстрації пароль хешується з використанням криптографічно стійкого алгоритму (наприклад, `bcrypt` або `argon2`) з додаванням унікальної «солі» (salt).
- API-ключі в базі даних також зберігаються як хеші (як паролі). Користувач бачить свій API-ключ цілком лише один раз — у момент генерації. Надалі в інтерфейсі відображаються лише перші та останні символи (наприклад, `sk_live_...a7f2`).

### 5.3. Захист ендпоїнтів авторизації

- Маршрути `/auth/login` і `/auth/register` захищені вбудованим механізмом обмеження кількості запитів (Rate Limiting).
- У разі серії невдалих спроб введення пароля (наприклад, понад 5 разів за хвилину) IP-адреса тимчасово блокується, що запобігає атакам типу Brute Force.

### 5.4. Інноваційний механізм відновлення доступу (Telegram Fallback)

Замість класичного (і часто нестабільного) надсилання листів із кодами підтвердження на email система використовує гібридний підхід до відновлення втраченого пароля, інтегруючи Telegram:

- **Прив'язка акаунта.** В особистому кабінеті користувач може опційно прив'язати свій Telegram-акаунт до профілю Convertly Hub через спеціального бота.
- **Сценарій відновлення.** Після натискання «Забули пароль?» на сторінці `/auth/login` користувач вводить свій Email.
- **Доставка ключа.** Якщо до профілю прив'язаний Telegram, система генерує криптографічно стійкий одноразовий токен (Magic Link) із терміном життя 15 хвилин. Telegram-бот миттєво надсилає це посилання користувачеві.
- **Безпека методу.** Перехід за посиланням із месенджера відразу авторизує користувача та переводить його на захищену сторінку скидання пароля. Це виключає ризик перехоплення email-трафіку й значно пришвидшує процес відновлення доступу.

## 6. Механізм роботи публічного API

### 6.1. Архітектура ендпоїнтів

Взаємодія з Core-рушієм платформи для сторонніх застосунків відбувається через єдиний захищений маршрут:

- **Метод и URL:** `POST /api/v1/convert`

### 6.2. Автентифікація API-запитів

- Кожен запит до ендпоїнта має містити HTTP-заголовок авторизації: `Authorization: Bearer <API_KEY>`.
- За відсутності заголовка, передавання порожнього значення або невідповідності хешу ключа базі даних сервер перериває обробку й негайно повертає HTTP-статус `401 Unauthorized`.

### 6.3. Формат вхідних даних (Request)

Оскільки API працює з файлами, стандартний формат JSON не застосовується для тіла запиту.

- **Content-Type:** обов'язково `multipart/form-data`.
- **Тіло запиту (Payload) містить:**
  - `file`: сам бінарний файл (вихідний);
  - `targetFormat`: рядковий параметр, що вказує бажаний формат на виході (наприклад, `png` або `pdf`).

### 6.4. Формат вихідних даних (Response)

Відповідь сервера динамічно змінюється залежно від налаштувань приватності користувача (положення перемикача в дашборді), якому належить API-ключ:

- **Сценарій «Зберігання увімкнено»:** сервер повертає статус `200 OK` і JSON-об'єкт, що містить метадані файла та постійне посилання на його завантаження із S3-сховища.
- **Сценарій «Privacy Mode (без зберігання)»:** сервер повертає статус `200 OK`, а в тілі відповіді віддає безпосередньо бінарний потік (`Buffer/Stream`) сконвертованого файла. У заголовках відповіді зазначається `Content-Disposition: attachment; filename="result.pdf"`, що дає клієнтському застосунку змогу відразу почати завантаження.

### 6.5. Керування навантаженням (Rate Limiting)

Для запобігання DDoS-атакам і зловживанню ресурсами воркерів на рівні API реалізовано тротлінг:

- Встановлюється жорсткий ліміт (наприклад, 30 запитів за хвилину для одного API-ключа).
- У разі перевищення ліміту сервер не приймає файл в обробку та віддає HTTP-статус `429 Too Many Requests` із заголовком `Retry-After`, що вказує, через скільки секунд можна повторити запит.

## 7. Обробка непередбачених ситуацій (Edge Cases)

Оскільки SaaS-платформа приймає файли від зовнішніх користувачів, вона має бути максимально відмовостійкою та захищеною від зловмисних або помилкових дій. У системі реалізовано багаторівневу обробку винятків:

### 7.1. Перевищення допустимого розміру файла

- **Клієнтська валідація.** Під час спроби перетягнути файл, що перевищує ліміт (наприклад, > 10 МБ), зона Drag & Drop миттєво підсвічується червоним, завантаження блокується, а користувач бачить Toast-сповіщення. Трафік не витрачається.
- **Серверна валідація.** Якщо зловмисник обходить клієнтську перевірку (наприклад, надсилаючи великий файл напряму через cURL до API), backend перехоплює розмір потоку. Завантаження примусово обривається, і сервер повертає статус `413 Payload Too Large`.

### 7.2. Підміна формату (MIME-type spoofing)

- Система не довіряє розширенню файла, переданому клієнтом (наприклад, `document.docx`). Зловмисник може перейменувати виконуваний скрипт `.sh` або вірус `.exe` на `.docx`.
- Сервер аналізує «магічні байти» (file signatures) у заголовку завантаженого файла. Якщо реальний MIME-тип не відповідає заявленому або не входить до білого списку дозволених форматів, сервер негайно видаляє файл із пам'яті й повертає `415 Unsupported Media Type`.

### 7.3. Збої Core-рушія та пошкоджені файли

- Якщо користувач завантажує пошкоджений або зашифрований паролем `.docx`-файл, воркер (`Gotenberg`), що намагається його відкрити, може видати критичну помилку.
- Завдяки ізоляції процесів падіння воркера не призводить до падіння (Crash) основного сервера Next.js. Backend перехоплює цю помилку (через блок `try/catch`) і коректно транслює клієнтові статус `422 Unprocessable Entity` з поясненням: «Неможливо обробити файл. Переконайтеся, що архів не пошкоджено».

### 7.4. Мережеві таймаути

- У разі пікового навантаження, коли черга на конвертацію важких PDF-документів переповнена, запит може зависнути.
- На рівні API встановлено жорсткий таймаут (наприклад, 30 секунд). Якщо воркер не встиг віддати результат, сервер перериває з'єднання, очищає виділену пам'ять і повертає статус `504 Gateway Timeout`, пропонуючи повторити спробу пізніше.

## 8. Візуальні референси

З огляду на відсутність готових Figma-макетів, розробка інтерфейсу, найімовірніше, вестиметься за принципом Component-Driven Development із використанням бібліотеки готових UI-рішень.

### 8.1. Дизайн-система та стилістика

- Як основу використовується **Shadcn UI + Tailwind CSS**. Це забезпечить строгий, сучасний і консистентний вигляд без потреби промальовувати кожен піксель із нуля.
- **Загальний стиль.** Мінімалізм, рясне використання негативного простору (whitespace), чітка типографіка. Кольорова палітра монохромна (чорно-біла) з одним акцентним кольором (наприклад, глибоким синім або фіолетовим) для виділення активних станів.

### 8.2. Референси для ключових сторінок

- **Головна сторінка (конвертер).** Візуальним орієнтиром слугує сервіс **iLovePDF**. Зона завантаження файлів має посідати центральне місце. Головний акцент робиться на станах Drag & Drop: нейтральному, наведенні (Hover/Drag Over зі зміною кольору пунктирної рамки), процесі завантаження (анімований прогрес-бар) та успішному завершенні.
- **Особистий кабінет (Dashboard).** Орієнтиром виступають інтерфейси **Vercel** або **Stripe**. Бічна панель навігації (Sidebar), строгі картки налаштувань, тумблери (Toggles) для перемикання режимів і акуратні таблиці даних з історією конвертацій.
- **Документація API.** Орієнтир — **Tailwind UI Docs** або **Stripe API Reference**. Обов'язкове використання темної теми для блоків коду (Syntax Highlighting) і чіткої верстки таблиць із параметрами запитів, щоб документація виглядала як професійний продукт для розробників.
