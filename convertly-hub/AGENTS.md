# AGENTS.md — инструкции для Codex в Convertly Hub

## Старт работы

1. Прочитайте этот файл и только те связанные документы ниже, которые относятся к задаче.
2. Перед изменениями проверьте `git status --short`; не затирайте существующие незакоммиченные изменения.
3. Для разработки новой фичи, рефакторинга или исправления бага сначала создайте отдельную ветку. Исключение — прямое указание пользователя работать без новой ветки или в текущей ветке.
4. Не раскрывайте значения из `.env`, конфигураций с токенами и других секретов в сообщениях, логах или документации.

## MCP-серверы

Фактический список сверяйте командой `codex mcp list`. На момент последней проверки активны только следующие серверы:

| Сервер | Применение |
| --- | --- |
| `context7` | Актуальная документация библиотек и API перед интеграцией или исправлением ошибок. |
| `chrome-devtools` | Отладка уже открытого браузера: DOM, console, network и визуальные проблемы. |
| `playwright` | E2E-сценарии, воспроизведение пользовательских флоу и регрессионное UI-тестирование. |
| `github` | Репозитории, issues и pull requests на GitHub — только когда задача этого требует. |

Используйте лишь инструменты, реально предоставленные сервером в текущей сессии: не предполагайте имена методов из Gemini Code Assist или старых инструкций. GitLab и Atlassian MCP в текущем конфиге отсутствуют, поэтому не используйте связанные с ними правила.

## Проверка и документация

- Для изменений кода запускайте наиболее релевантные проверки: `npm test`, `npm run linteslint`, `npm run build` или целевой E2E-сценарий. Если изменено поведение, обновляйте связанные тесты; не запрещайте их изменение формальным правилом.
- Для UI-изменений проверьте отрендеренную страницу и хотя бы один целевой пользовательский сценарий. Для отладки используйте Chrome DevTools, для E2E — Playwright, если сервер доступен в сессии.
- По завершении задачи обновите [docs/progress.md](./docs/progress.md): задача, изменённые файлы, результаты проверок и новые переменные окружения. Обновляйте `docs/db-schema.md` и `docs/architecture.md`, если менялись соответственно схема БД или архитектура.

## Жизненный цикл задач и Git Workflow

Ты и любые твои субагенты ОБЯЗАНЫ строго следовать этому алгоритму при получении задачи на разработку новой фичи, рефакторинг или исправление бага.

### Шаг 1: Инициализация и выбор режима изоляции

- **По умолчанию** не пиши код напрямую в защищенных ветках (`main`, `master`, `dev`): сначала создай отдельную ветку.
- **Исключение:** если пользователь явно просит работать без новой ветки или в текущей ветке, следуй этому указанию.
- Перед началом работы вызови инструмент чтения файлов и проверь, существует ли файл `/docs/git-flow.md`.
  - **Если существует:** Прочитай его. Используй описанные там стандарты для названия веток, структуры коммитов и префиксов (feat, bug, chore и т.д.).
  - **Если не существует:** Используй стандартный подход (например, `feature/название-задачи` или `fix/описание-бага`).
- Перед внесением изменений определи режим своей работы:
  - **Сценарий А (Параллельная работа субагентов):** Если ты делегируешь задачи субагентам для параллельного выполнения или система уже выполняет другой процесс в этой директории, ты **ОБЯЗАН использовать Git Worktrees** Каждый параллельный процесс должен работать в своей изолированной папке на диске.
  - **Сценарий Б (Одиночный/Последовательный режим):** Если ты работаешь над задачей один и последовательно, используй стандартный флоу: просто создай ветку через `git checkout -b <branch-name>` в текущей директории.

### Шаг 2: Процесс разработки (Атомарные коммиты)

- Работай итеративно (строго внутри своей ветки или папки worktree).
- Как только ты успешно завершаешь крупный логический блок (настроил схему данных, дописал контроллер, тесты прошли успешно),ты **ОБЯЗАН автоматически создавать промежуточный коммит**.
- Не жди моей команды для этих коммитов. Это наша точка сохранения (savepoint) для безопасного отката.
- Пиши четкие сообщения коммитов по стандартам проекта.

### Шаг 3: Завершение и Ревью

- Когда ты выполнил все требования задачи и код работает, **ОСТАНОВИСЬ**.
- Сделай финальный коммит для своей ветки.
- Выведи мне краткий структурированный отчет: какие файлы изменены и какой функционал добавлен.
- В конце отчета задай прямой вопрос:
  - _Если использовался Сценарий Б:_ "Фича реализована. Проверяем работу, или я могу выполнить слияние (merge) с главной веткой?"
  - _Если использовался Сценарий А:_ "Изолированная работа завершена. Могу ли я слить ветку в main и удалить временный worktree?"
- **СТРОГИЙ ЗАПРЕТ:** Никогда не выполняй `git merge`, не удаляй worktree и не создавай Pull Request без моего прямого текстового разрешения "Да, сливай".

## Тестирование
При создании нового функционала создавай только самые важные unit, integration и component тесты.
При редактировании уже существующего функционала, тесты редактировать нельзя.
