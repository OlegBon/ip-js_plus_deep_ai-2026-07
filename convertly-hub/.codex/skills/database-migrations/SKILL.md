# Database Migrations

Безпечно змінюйте структуру даних у Convertly Hub: PostgreSQL і Prisma 7.

## Перед зміною

1. Прочитайте `prisma/schema.prisma`, пов'язані міграції та код, що працює зі змінюваними моделями.
2. Визначте, чи змінюється схема, дані, індекс або поведінка видалення. Оцініть обсяг таблиці, блокування та план відкоту.
3. Не змінюйте міграцію, яку могли застосувати у спільному середовищі: створіть нову.

## Безпечні патерни

- Нове поле до наявної таблиці додавайте nullable або з безпечним default; `NOT NULL` вводьте після backfill і перевірки даних.
- Розділяйте DDL і масову зміну даних. Виконуйте backfill порціями; не утримуйте довгу транзакцію.
- Для rename/remove застосовуйте expand-contract: сумісна схема, потім сумісний код застосунку, потім видалення старого поля.
- Додаючи relation, перевіряйте зовнішній ключ, `onDelete`, унікальність та індекс для реальних сценаріїв `JOIN` і фільтрації.
- Для великих таблиць окремо плануйте індекси й блокування. `CREATE INDEX CONCURRENTLY` не працює у транзакційному блоці.

## Команди та перевірка

- Перед застосуванням форматуйте схему й перевіряйте згенерований diff міграції.
- `prisma migrate dev`, `prisma migrate deploy`, `prisma db push`, `prisma migrate reset` і SQL, що змінює дані, запускайте лише після явного дозволу користувача.
- `migrate reset` допустимий лише для одноразової локальної бази розробки.
- Після дозволеного застосування перевірте статус міграцій, генерацію Prisma Client і сценарії доступу до змінених моделей.
- Оновіть `docs/db-schema.md`, а за зміни потоків даних — `docs/architecture.md` і `docs/progress.md`.

Не розкривайте `DATABASE_URL` та інші секрети.
