# Database Reviewer

Проводьте цільове рев'ю шару даних Convertly Hub. Мета — виявити проблеми схеми, міграцій і запитів до їхнього потрапляння в production, зберігаючи відповідність фактичному стану проєкту.

## Коли застосовувати

Застосовуйте навичку для проєктування або зміни Prisma-схеми, міграції, PostgreSQL-запиту, індексу, транзакції, пагінації або діагностики продуктивності бази даних. Для UI-змін, що не зачіпають дані, навичка не потрібна.

## Контекст проєкту

- Для реалізації міграції використовуйте `database-migrations`, для серверного коду Prisma — `prisma-patterns`, для поглибленого аналізу SQL та індексів — `postgres-patterns`.
- База даних — PostgreSQL; ORM — Prisma 7 з драйвером `@prisma/adapter-pg`.
- Актуальна схема міститься у `prisma/schema.prisma`, міграції — у `prisma/migrations/`.
- Локальна PostgreSQL запускається через `docker compose`; не розкривайте значення з `.env`.
- Поточний backend реалізовано частково: не видавайте проєктні рішення за вже наявну функціональність.

## Порядок рев'ю

1. Прочитайте змінену схему, міграцію та код, що її викликає. За потреби зіставте їх із `docs/db-schema.md` і `docs/architecture.md`.
2. Перевірте модель даних: відповідні типи, обов'язковість полів, унікальність, зовнішні ключі, поведінку `onDelete` й обмеження цілісності.
3. Перевірте доступ до даних: параметризацію, відсутність N+1, обсяг вибраних полів, пагінацію без великого `OFFSET` і коректні межі транзакцій.
4. Зіставте фільтри, `JOIN`, сортування та поля зовнішніх ключів з індексами. У складеному індексі спочатку мають іти поля точного збігу, потім діапазону або сортування.
5. Для складних або потенційно гарячих запитів запропонуйте `EXPLAIN (ANALYZE, BUFFERS)` на реалістичних даних. Не запускайте `EXPLAIN ANALYZE`, міграції, `db push`, `db execute` або команди зміни БД без явного дозволу користувача.
6. Окремо позначте критичні проблеми, рекомендації та припущення. Якщо доказів недостатньо, зазначте, які дані або план запиту потрібні.

## Обов'язкові перевірки

- Зовнішні ключі, що використовуються у зв'язках і фільтрах, мають обґрунтовані індекси.
- Грошові величини не зберігаються у `float`; для них підходить `numeric` або ціле число мінімальних одиниць.
- Часові мітки мають єдиний, явно обраний формат і часовий пояс там, де цього потребує бізнес-логіка.
- У production-коді немає необмеженого `SELECT *`, конкатенації введення користувача в SQL і довгих транзакцій під час мережевих викликів.
- Міграції розгортаються зворотно й безпечно: для великих таблиць враховуються блокування, backfill і створення індексів.
- Політики RLS та розмежування доступу розглядайте лише з появою multi-tenant або публічного доступу до даних; не додавайте їх формально до локального backend без такої вимоги.

## Результат

Сформуйте короткий звіт із пріоритетами `Критично`, `Важливо` та `Рекомендація`. Для кожного пункту зазначте файл або сутність, спостереження, ризик і конкретне виправлення. Якщо зауважень немає, перелічіть виконані перевірки та решту неперевірених припущень.
