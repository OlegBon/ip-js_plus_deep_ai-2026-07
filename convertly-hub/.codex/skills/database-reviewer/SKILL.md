# Database Reviewer

Проводите целевое ревью слоя данных Convertly Hub. Цель — выявить проблемы схемы, миграций и запросов до их попадания в production, сохранив соответствие фактическому состоянию проекта.

## Когда применять

Применяйте навык при запросе на проектирование или изменение Prisma-схемы, миграции, PostgreSQL-запроса, индекса, транзакции, пагинации либо при диагностике производительности базы данных. Для UI-изменений, не затрагивающих данные, навык не нужен.

## Контекст проекта

- Для реализации миграции используйте `database-migrations`, для серверного кода Prisma — `prisma-patterns`, для углублённого анализа SQL и индексов — `postgres-patterns`.
- База данных — PostgreSQL; ORM — Prisma 7 с драйвером `@prisma/adapter-pg`.
- Актуальная схема находится в `prisma/schema.prisma`, миграции — в `prisma/migrations/`.
- Локальная PostgreSQL запускается через `docker compose`; не раскрывайте значения из `.env`.
- Текущий backend реализован частично: не выдавайте проектные решения за уже работающую функциональность.

## Порядок ревью

1. Прочитайте изменённую схему, миграцию и вызывающий код. При необходимости сопоставьте их с `docs/db-schema.md` и `docs/architecture.md`.
2. Проверьте модель данных: подходящие типы, обязательность полей, уникальность, внешние ключи, поведение `onDelete` и ограничения целостности.
3. Проверьте доступ к данным: параметризацию, отсутствие N+1, объём выбираемых полей, пагинацию без большого `OFFSET` и корректные границы транзакций.
4. Сопоставьте фильтры, `JOIN`, сортировки и поля внешних ключей с индексами. Для составного индекса сначала должны идти поля точного равенства, затем диапазона или сортировки.
5. Для сложных или потенциально горячих запросов предложите `EXPLAIN (ANALYZE, BUFFERS)` на реалистичных данных. Не запускайте `EXPLAIN ANALYZE`, миграции, `db push`, `db execute` или команды изменения БД без явного разрешения пользователя.
6. Отметьте отдельно критичные проблемы, рекомендации и допущения. Если доказательств недостаточно, укажите, какие данные или план запроса нужны.

## Обязательные проверки

- Внешние ключи, используемые в связях и фильтрах, имеют обоснованные индексы.
- Денежные величины не хранятся в `float`; для них подходит `numeric` или целое число минимальных единиц.
- Временные метки имеют единый, явно выбранный формат и часовой пояс там, где это требуется бизнес-логикой.
- В production-коде нет неограниченного `SELECT *`, конкатенации пользовательского ввода в SQL и долгих транзакций во время сетевых вызовов.
- Миграции обратимо и безопасно разворачиваются: для больших таблиц учитываются блокировки, backfill и создание индексов.
- Политики RLS и разграничение доступа рассматриваются, только если появляется multi-tenant или публичный доступ к данным; не добавляйте их формально в локальный backend без такого требования.

## Результат

Сформируйте краткий отчёт с приоритетами `Критично`, `Важно` и `Рекомендация`. Для каждого пункта укажите файл или сущность, наблюдение, риск и конкретное исправление. Если замечаний нет, перечислите выполненные проверки и оставшиеся непроверенные предположения.
