# Локальні правила: архітектура

## 1. Архітектура й робота із сервером (Next.js App Router)

- **Стек:** проєкт використовує Next.js (App Router). Використовуй **серверні компоненти (Server Components)** за замовчуванням для отримання даних і зменшення розміру клієнтського бандла. Клієнтські компоненти (`"use client"`) застосовуй лише для інтерактивних елементів.
- **Асинхронність:** застосовуй сучасні асинхронні патерни (`async/await`) для роботи з API, особливо під час отримання даних у серверних компонентах.
- **Обробка станів:** обов'язково реалізуй обробку станів завантаження та помилок за допомогою вбудованих файлів Next.js:
    - `loading.tsx` для показу спінерів або скелетонів;
    - `error.tsx` для перехоплення помилок і показу резервного UI.
- **Стилізація:** використовуй виключно утилітарні класи **Tailwind CSS**. Заборонено роздувати глобальні CSS-файли. Винось повторно використовувані UI-патерни в окремі React-компоненти.

## 2. Патерни компонентів

- **Container / Presentational:** розділяй компоненти на «контейнери», що відповідають за завантаження даних і логіку, та «презентаційні», що лише отримують пропси й відображають UI. Це спрощує повторне використання й тестування.
- **Композиція > Успадкування:** завжди надавай перевагу композиції. Використовуй `children` для вставлення вмісту та рендер-пропси для передавання логіки рендерингу.
- **Складені компоненти (Compound Components):** для складних віджетів (таби, акордеони) використовуй складені компоненти, які спільно використовують стан через React Context.

## 3. Керування станом (State Management)

Обирай місце зберігання стану за таким принципом:

1.  **Локальний стан (`useState`):** якщо дані використовує лише один компонент.
2.  **Підняття стану (Lifting State Up):** якщо дані потрібні кільком дочірнім компонентам, підніми стан до їхнього найближчого спільного батьківського компонента.
3.  **Контекст (React Context):** для глобальних даних, які читають у багатьох місцях, але **рідко оновлюють** (тема, авторизація, локалізація).
4.  **Зовнішнє сховище (Zustand, Redux):** для складного глобального стану, який часто оновлюється або має зберігатися між сторінками.
5.  **Серверний стан (TanStack Query, SWR):** для даних, отриманих із сервера (кешування, мутації, оптимістичні оновлення). **Не дублюй серверний стан у клієнтських сховищах.**

## 4. Отримання даних (Data Fetching)

| Стратегія                               | Коли використовувати                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| `await fetch` у серверному компоненті | Для даних, необхідних під час першого рендеру сторінки. Без клієнтського кешування.        |
| TanStack Query / SWR                    | Для клієнтського кешування, мутацій, оптимістичних оновлень і фонової ревалідації. |
| `fetch` у `useEffect`                   | **Уникати.** Призводить до перегонів станів, не має кешу та повторних спроб.          |
