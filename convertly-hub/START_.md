## Шаг 1. Инициализация основы (Next.js + UI)

Создаем единую папку проекта и ставим фронтенд-базу.

1. **Устанавливаем Next.js:**
   В терминале выполняем команду:
   `npx create-next-app@latest convertly-hub`_При установке выбираем: TypeScript, Tailwind CSS, App Router (Yes)._
2. **Переходим в папку:**`cd convertly-hub`
3. **Инициализируем Shadcn UI:**`npx shadcn-ui@latest init`_Выбираем стиль (например, New York) и базовый цвет (Zinc/Slate)._
4. Формируем структуру папок (согласно архитектуре):
   Создаем пустые директории внутри проекта, чтобы сразу видеть скелет:

- `app/(auth)/login`, `app/(auth)/register`, `app/(dashboard)`
- `app/api/v1/convert`, `app/api/health` _(это будет наша точка проверки)_
- `components/auth`, `components/core`, `components/dashboard`
- `lib/`
- `core/`

## Шаг 2. Установка зависимостей бэкенда и ядра

Ставим только то, что нужно для инфраструктуры и обработки.

1.  **База данных (Prisma):**`npm install prisma --save-devnpm install @prisma/client`

## Шаг 3. Конфигурация локальной инфраструктуры (Docker)

Чтобы не засорять систему, поднимаем базу, S3 и воркер конвертации документов в контейнерах.

1. **Создаем файл `docker-compose.yml` в корне проекта.**
2. **Добавляем сервисы (краткая суть):**

- **Postgres:** Образ `postgres:15-alpine`. Пробрасываем порт 5432.
- **MinIO:** Образ `minio/minio`. Пробрасываем порты 9000 (API) и 9001 (Web UI). Команда запуска: `server /data --console-address ":9001"`.
- **Gotenberg:** Образ `gotenberg/gotenberg:8`. Пробрасываем порт 3000.

## Шаг 4. Базовые настройки файлов

Нам нужно прописать минимальные настройки, чтобы связать проект воедино.

1. **`.env` (Корень проекта):**
   Прописываем `DATABASE_URL` (строка подключения к локальному Postgres из Docker), креды от MinIO (например, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`) и секрет для `NEXTAUTH_SECRET`.

## Шаг 5. Как запустить и проверить проект (Точки контроля)

Вот как мы тестируем работоспособность всех слоев без написания самого конвертера.

### 1. Проверка инфраструктуры (Слой Docker)

- **Запуск:** `docker compose up -d`
- **Проверка базы:** База должна быть готова принимать подключения.
- **Проверка S3:** Открываем в браузере `http://localhost:9001` (или порт, указанный в compose) — должен открыться веб-интерфейс MinIO.
- **Проверка Воркера:** Открываем `http://localhost:3000/health` — Gotenberg должен ответить статусом `200 OK`.

### 2. Проверка базы данных и ORM (Слой Prisma)

- **Действие:** Выполняем `npx prisma db push`.
- **Проверка:** Prisma должна сообщить, что таблицы успешно созданы в PostgreSQL. Команда `npx prisma studio` откроет локальную админку базы в браузере. Если таблицы есть — слой БД работает.

### 3. Проверка Фронтенда (Слой Next.js)

- **Запуск:** `npm run dev`
- **Проверка:** Открываем `http://localhost:3000` (если порт свободен, по умолчанию используется 3000, но так как у нас на нем Gotenberg, Next.js сам предложит порт 3001). Должна открыться дефолтная страница Next.js с нашими Tailwind-стилями.

### 4. Проверка Бэкенда (API)

Вместо сложной конвертации мы пишем простой Health Check.

- **Действие:** В файле `app/api/health/route.ts` пишем функцию `GET`, которая делает три простые вещи:

1. Запрашивает `prisma.user.count()` (проверка связи с БД).
2. Делает `fetch('<http://localhost:3000/health>')` к контейнеру Gotenberg.
3. Возвращает JSON: `{ db: "ok", gotenberg: "ok" }`.

- **Проверка:** Дергаем `http://localhost:3001/api/health` через браузер или REST Client. Если вернулся JSON с "ok" — вся наша многослойная архитектура успешно "общается" между собой.

Команда инициализации `npx shadcn-ui@latest init` создает базовый шаблон, который немного расходится с кастомными настройками из вашего `DESIGN.md`. Это абсолютно нормальная ситуация при настройке проекта, но эти расхождения нужно будет вручную "подружить".

Вот в чем заключаются основные нюансы и как их решать:

## 1. Нейминг CSS-переменных (Токены)

- **Что делает Shadcn:** При инициализации он генерирует файл `globals.css` со своими стандартными переменными Tailwind (например, `-background`, `-foreground`, `-primary`, `-muted`).
- **Что в DESIGN.md:** Ваш дизайн-документ использует собственную семантику токенов: `-color-background`, `-color-text-primary`, `-color-accent`, `-space-2`.
- **Решение:** Вам (или вашему AI-ассистенту) потребуется зайти в `tailwind.config.ts` и переназначить дефолтные классы Tailwind на ваши переменные. Например, цвет `primary` в конфиге Tailwind нужно будет связать с `var(--color-accent)` из `DESIGN.md`.

## 2. Базовые цвета (Zinc/Slate vs. Хардкод)

- **Что делает Shadcn:** Выбор базового цвета "Zinc" или "Slate" в CLI автоматически пропишет оттенки из палитры Tailwind в `globals.css`.
- **Что в DESIGN.md:** Документ задает конкретные hex-коды. Например, `-color-text-primary: #1F2937` (это ближе к оттенку Gray-800) и `-color-border: #E5E7EB` (Gray-200).
- **Решение:** После работы CLI-утилиты Shadcn вам нужно будет просто скопировать блок `:root` из секции **Quick Start** вашего `DESIGN.md` и вставить его поверх того, что сгенерировал Shadcn, чтобы интерфейс соответствовал вашему стандарту.

## 3. Скругления (Border Radius)

- **Что делает Shadcn:** Стиль "New York" по умолчанию использует более мелкие скругления (обычно `0.3rem` или `0.5rem`) и более мелкий шрифт.
- **Что в DESIGN.md:** В документе жестко зафиксированы значения: `6px` для кнопок и инпутов, а также `8px` для карточек.
- **Решение:** В сгенерированном `globals.css` нужно будет обновить глобальную переменную `-radius`, чтобы она соответствовала вашим `6px` и `8px`.

В Next.js (в парадигме App Router) папки, название которых обернуто в круглые скобки, называются **Route Groups (Группы маршрутов)**. Это специальный синтаксис фреймворка, который решает сразу несколько важных задач:

## 1. Они не влияют на итоговый URL-адрес

В Next.js любая обычная папка внутри `app/` автоматически становится частью ссылки в браузере. Но если папка в скобках, фреймворк делает ее "невидимой" для роутинга:

- Файл, лежащий по пути `app/(auth)/login/page.tsx`, будет доступен по адресу `твой-домен.com/login` (а не `/auth/login`).
- Файл по пути `app/(dashboard)/docs/page.tsx` будет доступен по адресу `твой-домен.com/docs`.

## 2. Разные обертки (Layouts) для разных страниц

Это главная причина их использования. В Next.js можно создавать файлы `layout.tsx`, которые оборачивают страницы (например, добавляют хедер или футер). Группы маршрутов позволяют применить совершенно разный дизайн к разным частям сайта, не ломая общую структуру:

- Внутри `app/(auth)` можно положить свой `layout.tsx`, который будет рендерить страницы входа и регистрации на чистом белом фоне по центру экрана (без меню навигации).
- Внутри `app/(dashboard)` можно положить другой `layout.tsx`, который будет автоматически добавлять ко всем страницам внутри этой группы боковую панель (Sidebar), шапку профиля и проверять, авторизован ли пользователь.

## 3. Логическая организация

Когда проект разрастется, это поможет тебе не запутаться. Ты открываешь редактор и сразу видишь логические блоки: здесь всё для авторизации, здесь всё для личного кабинета, а публичные API-маршруты лежат отдельно.

Так что смело кликай "New Folder" и вводи название прямо со скобками: `(auth)` и `(dashboard)`.

## .env

1. **Как работает Next.js:** Он невероятно умный и автоматически читает переменные из целой иерархии файлов: `.env`, `.env.local`, `.env.development` и т.д. Ему без разницы, где лежат переменные, он их найдет.
2. **Как работает Prisma (CLI):** А вот утилиты Prisma (когда ты пишешь в терминале `npx prisma db push` или `npx prisma studio`) по умолчанию "глуповаты". Они ищут строку подключения к базе данных _строго_ в файле с именем `.env`. Если ты переименуешь его в `.env.local`, Prisma просто выдаст ошибку, что не может найти `DATABASE_URL` (придется каждый раз указывать путь к файлу вручную через флаги, что очень неудобно).

**Какой стандарт в индустрии для связки Next.js + Prisma:**
Файл оставляют с именем `.env`, чтобы Prisma работала "из коробки", и просто обязательно проверяют, чтобы строка `.env` была добавлена в файл `.gitignore`. Так секреты остаются только на твоем локальном компьютере и не улетают в репозиторий.

## 1. Шпаргалка: Последовательность запуска проекта

Каждый раз, когда ты садишься за работу (например, после перезагрузки компьютера), твой процесс должен выглядеть так:

### Шаг 1. Инфраструктура (Docker)

Сначала мы поднимаем наши «фоновые» сервисы: базу данных, хранилище и воркер конвертации.

- **Действие:** Запусти программу Docker Desktop на компьютере и дождись, пока она загрузится.
- **Команда в терминале (в корне проекта):**

```bash
docker compose up -d
```

_(Флаг `-d` означает detached — контейнеры запустятся в фоне и освободят терминал)._

### Шаг 2. Синхронизация базы (Prisma) — _Опционально_

Эти команды нужны **только** если ты вносил изменения в файл `schema.prisma` (например, добавил новое поле или таблицу) или если скачал проект на новый компьютер. Если схему не трогал, этот шаг пропускаем.

- **Применить изменения в БД:**

```bash
npx prisma db push
```

- **Обновить типы TypeScript:**

```bash
npx prisma generate
```

### Шаг 3. Запуск приложения (Next.js)

Когда база и сервисы готовы, запускаем сам фреймворк.

- **Команда:**

```bash
npm run dev
```

_(После этого проект доступен в браузере, обычно на `http://localhost:3000` или `3001`)._

### 🛑 Как всё остановить

Когда заканчиваешь работу, в терминале, где работает `npm run dev`, нажми **`Ctrl + C`**. Чтобы остановить фоновые контейнеры Docker (чтобы не ели оперативку), выполни:

```bash
docker compose down
```

## 2. Как добавлять данные в базу

У тебя есть два основных пути работы с данными: ручной (для тестов) и программный (для реальной работы приложения).

### Способ А: Визуально (через Prisma Studio)

Это самый простой способ для проверки. Идеально подходит, чтобы быстро добавить тестового пользователя или посмотреть, сохранился ли лог.

1. Выполни в терминале:

```bash
npx prisma studio
```

1. Откроется вкладка в браузере.
2. Кликни на таблицу `User`.
3. Нажми кнопку **"Add record"** (Добавить запись).
4. Заполни поля (например, введи email и любой пароль; `id`, `createdAt` и `updatedAt` заполнятся сами).
5. Нажми зеленую кнопку **"Save 1 change"** вверху. Данные в базе!

### Способ Б: Программно (через код TypeScript)

Именно так будет работать твой Convertly Hub. Когда пользователь будет регистрироваться на сайте, твой API-маршрут выполнит примерно такой код.

Вот пример того, как это выглядит на практике (можешь сохранить этот сниппет на будущее):

```tsx
import { PrismaClient } from "@prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const adapter = new PrismaPg(pool);
const prisma = new PrismaClient({ adapter });

async function createTestUser() {
  // Вызываем метод create у модели user
  const newUser = await prisma.user.create({
    data: {
      email: "test@example.com",
      password: "hashed_password_here", // В реальности пароль нужно хэшировать!
    },
  });

  console.log("Создан пользователь:", newUser);
}
```

База данных работает **внутри контейнера** (`convertly_db`), но переживать за сохранность данных при перезапуске **не нужно** — они не пропадут.

Вот как это устроено "под капотом":

1. **Контейнер ≠ Данные:** Сам контейнер с базой данных — это просто изолированная среда выполнения. Если ты его удалишь или остановишь (`docker compose down`), сам контейнер сотрется.
2. **Docker Volumes (Тома):** Для надежности в нашем `docker-compose.yml` прописан специальный механизм постоянного хранения — volume с именем `db_data`:

```yaml
volumes:
  db_data:
```

Этот том маппится (привязывается) к внутренней папке PostgreSQL, где физически лежат файлы базы данных (`/var/lib/postgresql/data`), но эти файлы хранятся **на хост-машине** (твоем компьютере) отдельно от жизненного цикла контейнера.

## Что происходит при разных действиях:

- **`docker compose stop`** (или остановка Docker Desktop): Контейнеры просто засыпают. Данные полностью на месте.
- **`docker compose down`**: Контейнеры удаляются, но **volume `db_data` сохраняется**. Когда ты снова введешь `docker compose up -d`, контейнер поднимется и подхватит все твои старые таблицы и записи.
- **`docker compose down -v`** (с флагом `v`): Вот это действие **удалит и тома** (volumes). Если выполнить его, все данные из базы действительно сотрутся. В обычной работе без острой необходимости этот флаг использовать не нужно.
