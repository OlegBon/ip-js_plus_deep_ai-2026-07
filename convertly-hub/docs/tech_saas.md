# ⚙️ Convertly Hub - SaaS File Converter & API Platform

Микро-сервис для быстрой конвертации файлов с предоставлением публичного API для разработчиков. Проект объединяет удобный пользовательский интерфейс и надежную серверную инфраструктуру обработки данных.

---

## 1. Введение и цели проекта

**Название проекта (рабочее):** Convertly Hub

**Основная суть продукта:**
Проект представляет собой веб-приложение (SaaS-платформу), предоставляющее услуги по быстрой конвертации файлов между различными форматами. Взаимодействие с сервисом осуществляется двумя путями: через графический пользовательский интерфейс (B2C сценарий для обычных пользователей) и через публичное REST API (B2B/Developer сценарий для интеграции в сторонние программные продукты).

**Основная цель:**
Разработка легковесного, но архитектурно масштабируемого сервиса для конвертации файлов, который включает в себя полноценную систему авторизации, управление профилем пользователя, генерацию уникальных ключей доступа и надежное ядро (Core) для обработки медиафайлов и документов.

**Ключевые задачи проекта:**

1. **Реализация Core-начинки.** Создание отказоустойчивого механизма приема, обработки и возврата файлов без критической нагрузки на основной сервер.
2. **Предоставление API.** Разработка защищенного эндпоинта, который позволит сторонним разработчикам отправлять файлы на конвертацию, используя уникальный API-ключ.
3. **Управление состоянием пользователя.** Создание личного кабинета с гибкими настройками приватности (возможность включать/отключать сохранение сконвертированных файлов на сервере).
4. **Построение UX/UI.** Разработка интуитивно понятного интерфейса для ручной загрузки файлов с корректной обратной связью при любых сценариях (успех, ошибка, превышение лимита).

## 2. Архитектура и технологический стек

### 2.1. Концепция архитектуры

Система строится по принципу разделения ответственности (Separation of Concerns) и концептуально делится на три независимых слоя. Такой подход обеспечивает отказоустойчивость, характерную для надежных корпоративных сервисов, и позволяет масштабировать каждый компонент отдельно:

- **Клиентская часть (Frontend).** Витрина сервиса и интерактивный личный кабинет пользователя.
- **Серверная часть и API (Backend).** Обработка бизнес-логики, аутентификация, маршрутизация и проверка лимитов.
- **Core-движок (Workers).** Изолированная среда для выполнения ресурсоемких задач по перекодированию файлов.

### 2.2. Основной фреймворк и интерфейс

- **Фреймворк: Next.js (App Router).** Выступает в роли главного оркестратора. Используется для серверного рендеринга (SSR) интерфейса и создания защищенных API-маршрутов.
- **Стилизация и UI: Tailwind CSS.** Гарантирует создание строгих, легковесных и переиспользуемых UI-компонентов без перегрузки клиентской части лишними CSS-библиотеками. Особое внимание уделяется визуальной обратной связи: микроинтеракциям, состояниям Drag & Drop зон и индикаторам прогресса.

### 2.3. Инфраструктура данных

- **Реляционная база данных.** PostgreSQL в связке с Prisma ORM. Отвечает за надежное хранение строго структурированных транзакционных данных: профилей пользователей, хэшей паролей, сгенерированных API-ключей и логов (истории) конвертаций. Сами файлы в БД не сохраняются.
- **Объектное хранилище.** S3-совместимое хранилище (например, MinIO или AWS S3). Обеспечивает потоковую загрузку (Streaming) и отдачу файлов. Использование независимого хранилища закладывает архитектурный потенциал для горизонтального масштабирования и управления большими объемами медиаданных (вплоть до выделения терабайтных пулов под аккаунт).

> **Уточнение по инфраструктуре хранилища:**
> Для MVP, защиты проекта и даже для начального запуска SaaS-продукта платить за хранилище на старте не придется. Архитектура S3 стала стандартом (API), поэтому есть несколько отличных бесплатных вариантов реализации:
>
> - **MinIO (Локально для разработки).** Это S3-совместимое хранилище, которое поднимается локально через Docker буквально одной командой. Оно не требует интернета и финансовых затрат. Идеально для написания кода и тестирования. Когда код работает с MinIO, он будет работать с любым другим S3-хранилищем без переписывания логики.
> - **Cloudflare R2 (Для продакшена).** Бесплатный тариф предоставляет 10 ГБ хранилища ежемесячно и нулевую стоимость исходящего трафика (egress fees). Для SaaS-конвертера, где пользователи постоянно скачивают файлы, это оптимальный выбор.
> - **AWS S3 Free Tier.** Amazon предоставляет 5 ГБ бесплатно на первые 12 месяцев.
> - **Supabase Storage.** При использовании Supabase в качестве базы данных (PostgreSQL), платформа предоставляет встроенное S3-хранилище (1 ГБ в бесплатном тарифе).
>
> _Таким образом, проект Convertly Hub может быть полностью реализован и запущен на базе бесплатных мощностей._

### 2.4. Core-движок и изоляция процессов (Решение проблемы Event Loop)

Поскольку JavaScript является однопоточным языком, выполнение сложных математических вычислений прямо на сервере бэкенда неминуемо приведет к блокировке Event Loop. Чтобы "тяжелый" файл не остановил работу всего сервиса для других клиентов, применяется раздельный подход:

- **Синхронная обработка (Легкие задачи).** Конвертация изображений (`JPG ↔ PNG`) выполняется с помощью высокопроизводительной библиотеки `sharp` (Node.js). Операция происходит на уровне C++, занимает миллисекунды и безопасно выполняется в основном процессе.
- **Изолированная обработка (Тяжелые задачи).** Конвертация документов (`DOCX → PDF`) делегируется отдельному микросервису (например, `Gotenberg`, развернутому в изолированном Docker-контейнере). Next.js здесь выступает исключительно как шлюз: принимает файл потоком, передает его по сети в независимый воркер, дожидается ответа и возвращает готовый PDF клиенту. Это гарантирует бесперебойную работу основного API и UI даже под пиковой нагрузкой.

### 2.5. Тестирование

- **Фреймворк для тестирования: Jest.** Стандарт де-факто для тестирования JavaScript-приложений, интегрированный с Next.js.
- **Библиотека для тестирования компонентов: React Testing Library.** Позволяет писать тесты, которые имитируют поведение пользователя, обеспечивая надежность и поддерживаемость.
- **`@testing-library/jest-dom`:** Расширение для Jest, добавляющее кастомные матчеры для работы с DOM.
- **`ts-jest`:** Пресет для Jest, позволяющий работать с TypeScript.
- **`@testing-library/user-event`:** Библиотека для симуляции взаимодействия пользователя с компонентами.
- **MSW (Mock Service Worker):** Библиотека для изолированного мокирования сетевых запросов в integration-тестах без обращения к реальным сервисам.
- **Покрытие:** unit-тесты для небольших UI-элементов, component-тесты для изолированных компонентов и integration-тесты для пользовательских потоков Dashboard/Admin.

## 3. Выбор форматов файлов и бизнес-логика

### 3.1. Поддерживаемые форматы (Scope для MVP)

В рамках первой версии продукта реализована поддержка двух наиболее востребованных направлений конвертации, каждое из которых демонстрирует разные архитектурные подходы к обработке данных:

- **Изображения (JPG ↔ PNG).** Демонстрирует мгновенную (синхронную) обработку легковесных медиафайлов. Выполняется потоково, не требует значительных ресурсов и позволяет протестировать пропускную способность API при множественных запросах.
- **Документы (DOCX → PDF).** Демонстрирует асинхронную обработку и работу Core-движка с тяжелыми форматами. Имеет высокую коммерческую ценность (B2B сегмент) и доказывает способность архитектуры не блокировать основной Event Loop сервера при сложных математических операциях рендеринга шрифтов и разметки.

### 3.2. Политика хранения и управление приватностью (User Control)

Ядром бизнес-логики платформы является строгий контроль пользователя над своими данными. Управление осуществляется через глобальный переключатель (Toggle) «Сохранять результаты конвертации», расположенный в личном кабинете.

Логика работы механизма:

- **Состояние «Активно» (По умолчанию).** Все загружаемые файлы (как через веб-интерфейс, так и через публичное API) после успешной конвертации сохраняются в S3-хранилище. В базе данных создается запись с метаданными файла, которая моментально отображается в таблице файлового менеджера в личном кабинете пользователя.
- **Состояние «Выключено» (Privacy Mode).** Система переходит в режим обработки «на лету» (In-Memory / Temp Storage). Сконвертированный файл возвращается клиенту в виде бинарного потока или временной защищенной ссылки (TTL 1 час) и немедленно удаляется с серверов платформы.
- **Изоляция состояний (Обратная совместимость).** Перевод переключателя в неактивное положение влияет исключительно на будущие конвертации. Файлы, которые уже находятся в профиле пользователя, не подвергаются автоматическому удалению и остаются доступны для скачивания до момента ручного удаления пользователем.

## 4. Структура страниц и пользовательские сценарии (UI/UX)

### 4.1. Главная страница (Landing & Conversion Zone)

- **URL:** `/`
- **Назначение:** Основная точка входа, демонстрирующая ключевую ценность сервиса без обязательной регистрации.
- **Структура блоков:** Hero-секция с описанием и два виджета Drag & Drop (зона загрузки изображений и зона загрузки документов). Индикатор прогресса конвертации и кнопка скачивания.

### 4.2. Блок авторизации (Auth Flow)

- **URL:** `/auth/login` и `/auth/register`
- **Назначение:** Идентификация пользователей для доступа к функционалу личного кабинета.
- **Структура блоков:** Минималистичные формы с полями Email и Password, а также ссылками на восстановление доступа.

### 4.3. Личный кабинет (Dashboard & Profile Management)

- **URL:** `/dashboard` (доступно только авторизованным пользователям)
- **Назначение:** Центр управления аккаунтом.
- **Структура блоков:**
  - **Управление профилем:** Редактирование личных данных.
  - **Управление API-доступом:** Блок с текущим API-ключом, кнопками копирования и регенерации.
  - **Настройки хранилища:** Переключатель «Сохранять сконвертированные файлы в профиле».
  - **Файловый менеджер:** Таблица с историей транзакций и ссылками на скачивание сохраненных файлов.

### 4.4. Страница документации API

- **URL:** `/docs`
- **Назначение:** Техническое руководство для сторонних разработчиков по интеграции конвертера.
- **Структура блоков:** Описание эндпоинтов, требования к аутентификации (Bearer токен), сниппеты кода (cURL, JS) и таблица расшифровки HTTP-ошибок.

### 4.5. Панель администратора (Admin Panel)

- **URL:** Скрытый эндпоинт (например, `/system-manage/login` или `/portal-access`). Строго исключен из файла `robots.txt` и карты сайта.
- **Назначение:** Внутренний инструмент для управления платформой и мониторинга ее состояния.
- **Структура блоков:**
  - **Дашборд метрик:** Общее количество пользователей, количество конвертаций за 24 часа, нагрузка на воркеры.
  - **Управление пользователями:** Поиск по Email, возможность принудительной блокировки аккаунта (Banned) или ручного сброса пароля.
  - **o Управление API-ключами:** Возможность отзыва (Revoke) ключей, на которые зафиксирована аномальная нагрузка или спам-активность.

## 5. Авторизация и управление доступом

### 5.1. Основной механизм аутентификации

Для обеспечения безопасности сессий и работы публичного API используется комбинированный подход:

- **Веб-клиент (Личный кабинет).** Аутентификация реализуется на базе библиотеки `NextAuth.js` (`Auth.js`) с использованием защищенных `HttpOnly` куки. Это стандартный и наиболее безопасный метод для Next.js приложений, защищающий токены сессии от XSS-атак (межсайтового скриптинга).
- **Публичное API.** Аутентификация происходит по статичному API-ключу (Bearer Token), который передается в заголовке запроса.

### 5.2. Политика хранения учетных данных

- Платформа не хранит пароли пользователей в открытом виде. При регистрации пароль хэшируется с использованием криптографически стойкого алгоритма (например, `bcrypt` или `argon2`) с добавлением уникальной "соли" (salt).
- API-ключи в базе данных также хранятся в виде хэшей (как пароли). Пользователь видит свой API-ключ целиком только один раз – в момент генерации. В дальнейшем в интерфейсе отображаются только первые и последние символы (например, `sk_live_...a7f2`).

### 5.3. Защита эндпоинтов авторизации

- Маршруты `/auth/login` и `/auth/register` защищены встроенным механизмом ограничения количества запросов (Rate Limiting).
- В случае серии неудачных попыток ввода пароля (например, более 5 раз за минуту) IP-адрес временно блокируется, что предотвращает атаки типа Brute Force.

### 5.4. Инновационный механизм восстановления доступа (Telegram Fallback)

Вместо классической (и часто нестабильной) отправки писем с кодами подтверждения на email, система использует гибридный подход для восстановления утерянного пароля, интегрируя Telegram:

- **Привязка аккаунта.** В личном кабинете пользователь может опционально привязать свой Telegram-аккаунт к профилю Convertly Hub через специального бота.
- **Сценарий восстановления.** При нажатии "Забыли пароль?" на странице `/auth/login`, пользователь вводит свой Email.
- **Доставка ключа.** Если к профилю привязан Telegram, система генерирует криптографически стойкий одноразовый токен (Magic Link) со сроком жизни 15 минут. Telegram-бот мгновенно присылает эту ссылку пользователю.
- **Безопасность метода.** Переход по ссылке из мессенджера сразу авторизует пользователя и переводит его на защищенную страницу сброса пароля. Это исключает риск перехвата email-трафика и значительно ускоряет процесс восстановления доступа.

## 6. Механизм работы публичного API

### 6.1. Архитектура эндпоинтов

Взаимодействие с Core-движком платформы для сторонних приложений происходит через единый защищенный маршрут:

- **Метод и URL:** `POST /api/v1/convert`

### 6.2. Аутентификация API-запросов

- Каждый запрос к эндпоинту обязан содержать HTTP-заголовок авторизации: `Authorization: Bearer <API_KEY>`.
- При отсутствии заголовка, передаче пустого значения или несовпадении хэша ключа с базой данных, сервер прерывает обработку и немедленно возвращает HTTP-статус `401 Unauthorized`.

### 6.3. Формат входящих данных (Request)

Поскольку API работает с файлами, стандартный формат JSON не применяется для тела запроса.

- **Content-Type:** Обязательно `multipart/form-data`.
- **Тело запроса (Payload) включает:**
  - `file`: Сам бинарный файл (исходник).
  - `targetFormat`: Строковый параметр, указывающий желаемый формат на выходе (например, `png` или `pdf`).

### 6.4. Формат исходящих данных (Response)

Ответ сервера динамически меняется в зависимости от настроек приватности пользователя (положения переключателя в дашборде), которому принадлежит API-ключ:

- **Сценарий "Хранение включено":** Сервер возвращает статус `200 OK` и JSON-объект, содержащий метаданные файла и постоянную ссылку на его скачивание из S3-хранилища.
- **Сценарий "Privacy Mode (Без хранения)":** Сервер возвращает статус `200 OK`, а в теле ответа отдает непосредственно бинарный поток (`Buffer/Stream`) сконвертированного файла. В заголовках ответа прописывается `Content-Disposition: attachment; filename="result.pdf"`, что позволяет клиентскому приложению сразу начать скачивание.

### 6.5. Управление нагрузкой (Rate Limiting)

Для предотвращения DDoS-атак и злоупотребления ресурсами воркеров на уровне API реализован троттлинг:

- Устанавливается жесткий лимит (например, 30 запросов в минуту для одного API-ключа).
- При превышении лимита сервер не принимает файл в обработку и отдает HTTP-статус `429 Too Many Requests` с заголовком `Retry-After`, указывающим, через сколько секунд можно повторить запрос.

## 7. Обработка непредвиденных ситуаций (Edge Cases)

Поскольку SaaS-платформа принимает файлы от внешних пользователей, она должна быть максимально отказоустойчивой и защищенной от злонамеренных или ошибочных действий. В системе реализована многоуровневая обработка исключений:

### 7.1. Превышение допустимого размера файла

- **Клиентская валидация.** При попытке перетащить файл, превышающий лимит (например, > 10 МБ), зона Drag & Drop мгновенно подсвечивается красным, загрузка блокируется, и пользователь видит Toast-уведомление. Трафик не расходуется.
- **Серверная валидация.** Если злоумышленник обходит клиентскую проверку (например, отправляя большой файл напрямую через cURL к API), бэкенд перехватывает размер потока. Загрузка принудительно обрывается, и сервер возвращает статус `413 Payload Too Large`.

### 7.2. Подмена формата (MIME-type spoofing)

- Система не доверяет расширению файла, переданному клиентом (например, `document.docx`). Злоумышленник может переименовать исполняемый скрипт `.sh` или вирус `.exe` в `.docx`.
- Сервер анализирует "магические байты" (file signatures) в заголовке загруженного файла. Если реальный MIME-тип не совпадает с заявленным или не входит в белый список разрешенных форматов, сервер немедленно удаляет файл из памяти и возвращает `415 Unsupported Media Type`.

### 7.3. Сбои Core-движка и поврежденные файлы

- Если пользователь загружает битый или зашифрованный паролем `.docx` файл, воркер (`Gotenberg`), пытающийся его открыть, может выдать критическую ошибку.
- Благодаря изоляции процессов, падение воркера не приводит к падению (Crash) основного сервера Next.js. Бэкенд перехватывает эту ошибку (через блок `try/catch`) и корректно транслирует клиенту статус `422 Unprocessable Entity` с пояснением: "Невозможно обработать файл. Убедитесь, что архив не поврежден".

### 7.4. Сетевые таймауты

- В случае пиковой нагрузки, когда очередь на конвертацию тяжелых PDF-документов переполнена, запрос может зависнуть.
- На уровне API установлен жесткий таймаут (например, 30 секунд). Если воркер не успел отдать результат, сервер прерывает соединение, очищает выделенную память и возвращает статус `504 Gateway Timeout`, предлагая повторить попытку позже.

## 8. Визуальные референсы

С учетом отсутствия готовых Figma-макетов, разработка интерфейса будет скорее всего вестись по принципу Component-Driven Development с использованием библиотеки готовых UI-решений.

### 8.1. Дизайн-система и стилистика

- В качестве основы используется **Shadcn UI + Tailwind CSS**. Это обеспечит строгий, современный и консистентный вид без необходимости отрисовывать каждый пиксель с нуля.
- **Общий стиль.** Минимализм, обильное использование негативного пространства (whitespace), четкая типографика. Цветовая палитра монохромная (черно-белая) с одним акцентным цветом (например, глубоким синим или фиолетовым) для выделения активных состояний.

### 8.2. Референсы для ключевых страниц

- **Главная страница (Конвертер).** Визуальным ориентиром служит сервис **iLovePDF**. Зона загрузки файлов должна занимать центральное место. Главный акцент делается на состояниях Drag & Drop: нейтральное, наведение (Hover/Drag Over с изменением цвета пунктирной рамки), процесс загрузки (анимированный прогресс-бар) и успешное завершение.
- **Личный кабинет (Dashboard).** Ориентиром выступают интерфейсы **Vercel** или **Stripe**. Боковая панель навигации (Sidebar), строгие карточки настроек, тумблеры (Toggles) для переключения режимов и аккуратные таблицы данных с историей конвертаций.
- **Документация API.** Ориентир – **Tailwind UI Docs** или **Stripe API Reference**. Обязательно использование темной темы для блоков с кодом (Syntax Highlighting) и четкой верстки таблиц с параметрами запросов, чтобы документация выглядела как профессиональный продукт для разработчиков.
