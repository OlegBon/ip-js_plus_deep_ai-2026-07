# План виконання робіт: Convertly Hub

Цей план складено на основі технічного завдання й архітектурної документації.

## Незавершені завдання — історичний огляд

Цей документ зберігає історію вихідного плану та виконаних етапів. З 7 вересня
2026 єдиний активний список майбутніх завдань міститься в
[docs/backlog](./backlog/README.md): він розділений за темами, не дублює
виконані завдання й оновлюється під час кожного рішення. Нижче залишено історичний
контекст, тому його пріоритети не є поточним планом робіт.

Позначення: `+` — завдання вже можна виконувати; `-` — поки не беремо в роботу. Цифра — загальний пріоритет, де `1` найвищий.

PowerShell API-сценарій винесено до
[api-powershell.md](./api-powershell.md), а логічний Supabase backup — до
[supabase-logical-backup.md](./supabase-logical-backup.md).

1. **(-, 10) Платежі й тарифи — заморожено до вибору провайдера**
   - **Чому не завершено:** тарифи та `PaymentModal` поки є демонстраційним UI; провайдера не вибрано, тому відсутні checkout, перевірка webhook, ідемпотентна синхронізація підписки та керування доступом.
   - **Як виконати:** після вибору провайдера визначити модель підписок і країни/валюти, реалізувати checkout, customer portal, верифікацію та ідемпотентну обробку webhook, потім пов’язати тариф із правами користувача й додати контрактні тести.
   - **Коли:** навмисно відкладено; не входить до найближчого локального MVP і поновлюється лише після продуктового рішення про провайдера.

2. **(-, 9) Backend‑5 — `PDF → DOCX`**
   - **Чому не завершено:** PDF зазвичай не містить повної структури вихідного документа, а Gotenberg не надає якісної зворотної конвертації; поточний Core підтримує лише `JPG ↔ PNG` і `DOCX → PDF`.
   - **Як виконати:** вибрати спеціалізований best-effort рушій, підготувати еталонні PDF/DOCX і критерії прийнятної втрати форматування, додати чергу/таймаути та окремі quality-тести.
   - **Коли:** після підтвердження бізнес-цінності напряму й вибору рушія; не блокує поточний MVP.

3. **(-, 8) Backend‑8 — спільний rate limiter для кількох інстансів**
   - **Чому не завершено:** поточний ліміт 30 запитів за хвилину на API-ключ зберігається в пам’яті одного процесу; за кількох екземплярів застосунку ліміти будуть незалежними.
   - **Як виконати:** підключити Redis-сумісне сховище, застосувати атомарний sliding/fixed-window алгоритм, додати health-check, метрики та інтеграційні тести конкурентних запитів.
   - **Коли:** до горизонтального масштабування або production-розгортання з кількома репліками Next.js.

4. **(-, 7) Backend‑9 — продуктивність пошуку адмінпанелі на великій БД**
   - **Чому не завершено:** cursor-pagination уже виключає великий `OFFSET`, але пошук підрядком за ім’ям/email через `contains` не має спеціалізованого PostgreSQL-індексу.
   - **Як виконати:** зняти `EXPLAIN (ANALYZE, BUFFERS)` на реалістичних даних, за потреби додати міграцію з `pg_trgm` і GIN-індексами, потім порівняти план і час відповіді.
   - **Коли:** у разі зростання таблиці користувачів або перед production-навантаженням; не потрібно для поточного MVP-обсягу даних.

5. **Інші завдання‑2 — реальні backend integration/E2E тести** (виконано)
   - [x] Додано ізольовані PostgreSQL, MinIO, Gotenberg і MailHog на окремих портах, test runner з міграціями та очищенням даних.
   - [x] Реальний HTTP-сценарій перевіряє auth/session, API-ключ, збереження/скачування із S3, режим без зберігання, guest-квоти, `DOCX → PDF` і admin API.
   - [x] GitHub Actions запускає набір окремою job без зміни наявних Jest і browser Playwright перевірок.

6. **Повноцінне відновлення пароля через Telegram** (виконано)
   - [x] Webhook зберігає нормалізований public username лише разом із підтвердженим chat ID, а recovery за `@username` створює одноразовий hashed token і надсилає reset URL Bot API винятково в активний підтверджений chat.
   - [x] Використовуються нейтральні відповіді проти user enumeration, локальний rate limit, обробка відсутнього username і Jest-тести webhook/Bot API.
   - [x] У production застосовано migration, розгорнуто app, налаштовано `setWebhook`, перевірено прив’язку з Dashboard, доставку reset-посилання в private chat за `@username`, зміну пароля та повторний вхід.

7. **Інші завдання‑3 — cloud deployment** (Northflank + Supabase demo виконано)
   - [x] Розгорнуто публічне функціональне demo `convertly-hub.bon.kharkov.ua`: Northflank public Next.js app, private Gotenberg, Supabase PostgreSQL і private S3-compatible Storage. Налаштовано DNS, TLS, SMTP, controlled Prisma migration job і smoke-tests.
   - [x] Для окремого Oracle A1 instance підготовлено ARM64-compatible Dockerfile, production Compose, Caddy HTTPS, `.env.production.example` і [Oracle runbook](./oracle-production-deployment.md). Також підготовлено runbook-плани для [Vercel Pro](./vercel-production-deployment.md) і [Render](./render-production-deployment.md).
   - [ ] Oracle VM, повноцінні off-host backup/restore, monitoring/alerting, CD та оцінку multi-instance rate limiting не виконано. Це не помилка поточного demo, а окрема тема [operations backlog](./backlog/040-operations-and-reliability.md).
   - **Наступний крок:** у разі зміни provider використовувати лише [cloud portability runbook](./cloud-portability.md): backup PostgreSQL/S3 → restore → migration job → private smoke-test → DNS cutover.

8. **(+, 3) Адмінська історія конвертацій і failed conversions**
   - **Чому не завершено:** System Monitoring показує число `FAILED`, але адміністратор може побачити конкретні записи й `errorMessage` лише у Prisma Studio. В Admin Panel немає історії конвертацій, failed-фільтра, пошуку, сортування та керованого видалення результатів.
   - **Як виконати:** додати окремі захищені `ADMIN` API та контейнер історії з server-side search/sort/cursor-pagination, фільтром статусу `FAILED`, відображенням безпечної діагностичної деталі й масовим вибором для підтвердженого видалення збережених файлів. Нейтральні `Search`/`CursorPagination` повторно використати, destructive-дії та права залишити в admin-container.
   - **Коли:** можна виконувати після поточної стабілізації Admin Panel; до production бажано, щоб показник failed conversions був операційно корисним.
