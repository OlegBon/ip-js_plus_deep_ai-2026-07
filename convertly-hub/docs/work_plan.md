# План выполнения работ: Convertly Hub

Этот план составлен на основе технического задания и архитектурной документации.

## Незавершённые задачи — приоритетный обзор

Этот раздел дублирует все незакрытые пункты из тематических разделов ниже, чтобы следующий этап работы был виден сразу. Канонические чекбоксы остаются в исходных разделах; после выполнения обновляются оба места.

Обозначения: `+` — задачу можно выполнять уже сейчас; `-` — пока не берём в работу. Цифра — общий приоритет, где `1` самый высокий.

1. **(-, 10) Платежи и тарифы — заморожено до выбора провайдера**
   - **Почему не завершено:** тарифы и `PaymentModal` пока являются демонстрационным UI; не выбран провайдер и поэтому отсутствуют checkout, проверка webhook, идемпотентная синхронизация подписки и управление доступом.
   - **Как выполнить:** после выбора провайдера определить модель подписок и страны/валюты, реализовать checkout, customer portal, верификацию и идемпотентную обработку webhook, затем связать тариф с правами пользователя и добавить контрактные тесты.
   - **Когда:** намеренно отложено; не входит в ближайший локальный MVP и возобновляется только после продуктового решения о провайдере.

2. **(-, 9) Backend‑5 — `PDF → DOCX`**
   - **Почему не завершено:** PDF обычно не содержит полной структуры исходного документа, а Gotenberg не даёт качественную обратную конвертацию; текущий Core поддерживает только `JPG ↔ PNG` и `DOCX → PDF`.
   - **Как выполнить:** выбрать специализированный best-effort движок, подготовить эталонные PDF/DOCX и критерии приемлемой потери форматирования, добавить очередь/таймауты и отдельные quality-тесты.
   - **Когда:** после подтверждения бизнес-ценности направления и выбора движка; не блокирует текущий MVP.

3. **(-, 8) Backend‑8 — общий rate limiter для нескольких инстансов**
   - **Почему не завершено:** текущий лимит 30 запросов в минуту на API-ключ хранится в памяти одного процесса; при нескольких экземплярах приложения лимиты будут независимыми.
   - **Как выполнить:** подключить Redis-совместимое хранилище, применить атомарный sliding/fixed-window алгоритм, добавить health-check, метрики и интеграционные тесты конкурирующих запросов.
   - **Когда:** до горизонтального масштабирования или production-развёртывания с несколькими репликами Next.js.

4. **(-, 7) Backend‑9 — производительность поиска админ-панели на большой БД**
   - **Почему не завершено:** cursor-pagination уже исключает большой `OFFSET`, но поиск подстрокой по имени/email через `contains` не имеет специализированного PostgreSQL-индекса.
   - **Как выполнить:** снять `EXPLAIN (ANALYZE, BUFFERS)` на реалистичных данных, при необходимости добавить миграцию с `pg_trgm` и GIN-индексами, затем сравнить план и время ответа.
   - **Когда:** при росте таблицы пользователей или перед production-нагрузкой; не требуется для текущего MVP-объёма данных.

5. **Прочие задачи‑2 — реальные backend integration/E2E тесты** (выполнено)
   - [x] Добавлены изолированные PostgreSQL, MinIO, Gotenberg и MailHog на отдельных портах, test runner с миграциями и очисткой данных.
   - [x] Реальный HTTP-сценарий проверяет auth/session, API-ключ, сохранение/скачивание из S3, режим без хранения, guest-квоты, `DOCX → PDF` и admin API.
   - [x] GitHub Actions запускает набор отдельной job без изменения существующих Jest и browser Playwright проверок.

6. **(-, 8) Полноценное восстановление пароля через Telegram**
   - **Почему не завершено:** текущая привязка хранит только защищённый chat ID после `/start link_…`; пароль можно восстановить по email, а ввод `@username` лишь валидируется. У бота нет сохранённого username и нет исходящей доставки reset-ссылки, поэтому нельзя создавать видимость работающего Telegram-reset.
   - **Как выполнить:** при webhook-привязке безопасно сохранять нормализованный публичный Telegram username (если он есть), сопоставлять только подтверждённый аккаунт, создавать уже существующий одноразовый хешированный токен и отправлять ссылку в связанный chat через Bot API. Нужны нейтральные ответы против user enumeration, общий rate limit, сценарий отсутствующего username, тесты webhook/Bot API и отдельные integration/E2E-проверки.
   - **Когда:** после согласования Telegram как канала восстановления и до production-релиза; не блокирует текущий локальный MVP, где надёжным каналом остаётся email.

7. **(+, 1) Прочие задачи‑3 — production deployment** (подготовка выполнена, выбор target ожидается)
   - **Что готово:** для предпочтительного отдельного Oracle A1 instance в Frankfurt добавлены ARM64-compatible Dockerfile, production Compose, Caddy HTTPS, безопасный `.env.production.example` и подробный [Oracle runbook](./oracle-production-deployment.md). Также подготовлены плановые runbook-документы для [Vercel Pro](./vercel-production-deployment.md), [Render Paid / Free demo](./render-production-deployment.md) и функционального [Northflank Free + Supabase Free demo](./northflank-supabase-demo.md) с отдельным [пошаговым setup guide](./northflank-supabase-setup.md). Они не создают облачные ресурсы и не заменяют Oracle-конфигурацию.
   - **Что ещё не выполнено:** Oracle VM пока недоступна по capacity; DNS A-запись, SMTP и реальный публичный запуск не созданы. Для Vercel/Render не выбраны managed PostgreSQL, S3 и закрытый worker. Во всех вариантах не настроены off-host backup/restore, мониторинг/alerting и CD. Rate limiter остаётся допустимым только для одного экземпляра Next.js.
   - **Как выполнить:** после выбора target выполнить только соответствующий runbook отдельной инфраструктурной задачей: создать VM или managed services, закрыть внутренние сервисы, заполнить server-only production secrets, применить миграции и провести smoke-tests. До пользовательских файлов настроить и проверить восстановление PostgreSQL и object storage во внешнем хранилище.
   - **Когда:** Oracle остаётся первым выбором после доступности A1 VM. Пока capacity недоступна, Northflank + Supabase — допустимый функциональный demo без схлопывания Gotenberg/MinIO; Vercel Pro или Render Paid — осознанные платные альтернативы. Render Free + MailHog не является public production. Go-live — только после успешных smoke-tests и принятого backup-плана.

8. **(+, 3) Админская история конвертаций и failed conversions**
   - **Почему не завершено:** System Monitoring показывает число `FAILED`, но администратор может увидеть конкретные записи и `errorMessage` только в Prisma Studio. В Admin Panel нет истории конвертаций, фильтра failed, поиска, сортировки и управляемого удаления результатов.
   - **Как выполнить:** добавить отдельные защищённые `ADMIN` API и контейнер истории с server-side search/sort/cursor-pagination, фильтром статуса `FAILED`, отображением безопасной диагностической детали и массовым выбором для подтверждённого удаления сохранённых файлов. Нейтральные `Search`/`CursorPagination` переиспользовать, destructive-действия и права оставить в admin-container.
   - **Когда:** можно выполнять после текущей стабилизации Admin Panel; до production желательно, чтобы показатель failed conversions был операционно полезен.
