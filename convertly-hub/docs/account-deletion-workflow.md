# Процесс удаления аккаунта

## Назначение

Удаление аккаунта — серверный процесс с участием двух сторон. Вошедший пользователь создаёт запрос
в **Dashboard → Profile**. Активный администратор рассматривает и подтверждает его в **Admin Panel →
Account Deletion Requests**. Штатный путь намеренно не использует одноразовую job.

## Состояния и аудит

`AccountDeletionRequest` хранит снимок email заявителя и допускает один активный запрос для
существующего пользователя. `AccountDeletionEvent` записывает события `REQUESTED`, `PROCESSING`,
`COMPLETED` и `FAILED` с email действующего лица и временем.

Связь запроса с `User` использует `ON DELETE SET NULL`. Поэтому запрос и аудит остаются доступны
после удаления пользователя и его каскадных записей, но идентификатор пользователя очищается. Это
сохраняет операционное подтверждение без хранения удалённого аккаунта.

| Статус       | Значение                                                      | Следующее действие                               |
| ------------ | ------------------------------------------------------------- | ------------------------------------------------ |
| `PENDING`    | Пользователь отправил запрос.                                 | Администратор может подтвердить его.             |
| `PROCESSING` | Администратор взял запрос в обработку.                        | Параллельное подтверждение запрещено.            |
| `COMPLETED`  | Файлы хранилища и данные аккаунта удалены.                    | Конечное состояние.                              |
| `FAILED`     | Удаление в хранилище или базе данных не завершилось.          | Администратор может безопасно повторить попытку. |
| `CANCELLED`  | Запрос отменён пользователем или администратором до удаления. | История и audit trail сохранены.                 |

Повторная отправка пользователем возвращает существующий запрос `PENDING` или `PROCESSING`.
Неудачный запрос можно создать повторно: записывается новое audit-событие `REQUESTED`, а статус
возвращается к `PENDING`.

Пользователь может отменить только собственный запрос `PENDING`. Администратор может отменить
`PENDING` или `FAILED`; `PROCESSING` не отменяется, поскольку сервер уже мог начать удаление S3.
Отменённый запрос остаётся в журнале со статусом `CANCELLED`, а при следующей заявке безопасно
переиспользуется с новым событием `REQUESTED`.

## Последовательность подтверждения

1. Администратор подтверждает действие в модальном окне. Сервер проверяет, что это активный admin,
   и не позволяет администратору подтвердить удаление собственного аккаунта.
2. Запрос атомарно переводится в `PROCESSING`; сначала создаётся событие, поэтому два
   администратора не могут одновременно удалить один аккаунт.
3. Сервер читает сохранённые у пользователя значения `ConversionLog.storageKey` и удаляет каждый
   S3-объект. S3 `DeleteObject` идемпотентен, поэтому повтор после частичного сбоя безопасен.
4. Сервер удаляет `User`. Prisma/база данных каскадно удаляет подписку, API-ключи и журналы
   конвертаций. Затем запрос получает статус `COMPLETED` и записывается событие.
5. Если любой этап в S3 или базе данных завершился ошибкой, пользователь остаётся (кроме случая,
   когда транзакция удаления уже была подтверждена), запрос получает `FAILED`, а администратор может
   повторить действие из панели.

Profile проверяет незавершённый запрос каждые 30 секунд. Если удаление завершено, следующий ответ
сообщает, что пользователь уже отсутствует: браузер очищает NextAuth-сессию и перенаправляет на
Главную с однократным уведомлением. После отмены запрос исчезает из Profile, а исходная кнопка
`Delete Account` снова доступна.

Не удаляйте пользователя вручную через Supabase Studio в рамках обычной поддержки: это обходит
последовательность очистки S3.

## Почтовые уведомления

Приложение отправляет операционные уведомления на `SUPPORT_EMAIL` при создании запроса, успехе,
сбое или отмене. В app logs успешная передача SMTP-провайдеру фиксируется как
`Account deletion support notification sent` с безопасными полями `kind` и `requestId`; при сбое
записывается безопасная SMTP-диагностика без пароля, адресов и тела письма. Доставка письма никогда не меняет статус удаления: недоступность SMTP не должна скрыть
запрос или вызвать повторное удаление. Добавьте
`SUPPORT_EMAIL=support@bon.kharkov.ua` в runtime group приложения Northflank — это не секрет.
Ящик и SMTP-переменные должны оставаться настроенными по cloud runbook.

## Чек-лист для production

1. Запустите migration job до deployment сборки приложения с этой функцией.
2. Добавьте `SUPPORT_EMAIL` в `convertly-app-runtime`, затем выполните deploy/restart приложения.
3. Используйте два тестовых аккаунта: обычный пользователь создаёт запрос, другой администратор
   подтверждает его. Один и тот же администратор не может подтвердить собственный запрос.
4. Убедитесь в Supabase, что завершённый запрос и события остались, а его `userId` стал `NULL`.
5. Убедитесь, что private S3 bucket не содержит объектов конвертаций удалённого пользователя, а в
   support mailbox пришли письма о запросе и завершении.

Первая migration функции: `20260907150000_account_deletion_workflow`.
