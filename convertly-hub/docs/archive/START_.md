## Крок 1. Ініціалізація основи (Next.js + UI)

Створюємо єдину папку проєкту й встановлюємо фронтенд-основу.

1. **Встановлюємо Next.js:**
   У терміналі виконуємо команду:
   `npx create-next-app@latest convertly-hub`_Під час встановлення обираємо: TypeScript, Tailwind CSS, App Router (Yes)._
2. **Переходимо до папки:**`cd convertly-hub`
3. **Ініціалізуємо Shadcn UI:**`npx shadcn-ui@latest init`_Обираємо стиль (наприклад, New York) і базовий колір (Zinc/Slate)._
4. Формуємо структуру папок (відповідно до архітектури):
   Створюємо порожні директорії всередині проєкту, щоб одразу бачити каркас:

- `app/(auth)/login`, `app/(auth)/register`, `app/(dashboard)`
- `app/api/v1/convert`, `app/api/health` _(це буде наша точка перевірки)_
- `components/auth`, `components/core`, `components/dashboard`
- `lib/`
- `core/`

## Крок 2. Встановлення залежностей бекенду та ядра

Встановлюємо лише те, що потрібно для інфраструктури та обробки.

1.  **База даних (Prisma):**`npm install prisma --save-devnpm install @prisma/client`
    Ініціалізуємо: `npx prisma init` (буде створено папку `prisma/` і файл `.env`).
    Редагуємо файл `.env`.
2.  **Авторизація:**`npm install next-auth bcryptnpm install @types/bcrypt --save-dev`
3.  **Сховище S3:**`npm install @aws-sdk/client-s3` (офіційний клієнт для роботи з MinIO/AWS).
4.  **Core-рушій (зображення):**`npm install sharp` (для синхронних задач в основному процесі).

## Крок 3. Конфігурація локальної інфраструктури (Docker)

Щоб не засмічувати систему, запускаємо базу, S3 і воркер конвертації документів у контейнерах.

1. **Створюємо файл `docker-compose.yml` у корені проєкту.**
2. **Додаємо сервіси (коротко про суть):**

- **Postgres:** Образ `postgres:15-alpine`. Пробросьте порт 5432.
- **MinIO:** Образ `minio/minio`. Пробросьте порти 9000 (API) і 9001 (Web UI). Команда запуску: `server /data --console-address ":9001"`.
- **Gotenberg:** Образ `gotenberg/gotenberg:8`. Пробросьте порт 3000.

## Крок 4. Базові налаштування файлів

Потрібно прописати мінімальні налаштування, щоб зв'язати проєкт у єдине ціле.

1. **`.env` (корінь проєкту):**
   Прописуємо `DATABASE_URL` (рядок підключення до локального Postgres із Docker), облікові дані MinIO (наприклад, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`) і секрет для `NEXTAUTH_SECRET`.
2. **`prisma/schema.prisma`:**
   Описуємо дві базові моделі (без глибокої логіки), щоб просто перевірити з'єднання: `User` (email, password) і `ConversionLog` (fileName, status).

## Крок 5. Як запустити та перевірити проєкт (контрольні точки)

Ось як ми тестуємо працездатність усіх шарів без написання самого конвертера.

### 1. Перевірка інфраструктури (шар Docker)

- **Запуск:** `docker compose up -d`
- **Перевірка бази:** База має бути готова приймати підключення.
- **Перевірка S3:** Відкриваємо у браузері `http://localhost:9001` (або порт, указаний у compose) — має відкритися вебінтерфейс MinIO.
- **Перевірка воркера:** Відкриваємо `http://localhost:3000/health` — Gotenberg має відповісти статусом `200 OK`.

### 2. Перевірка бази даних та ORM (шар Prisma)

- **Дія:** Виконуємо `npx prisma db push`.
- **Перевірка:** Prisma має повідомити, що таблиці успішно створені в PostgreSQL. Команда `npx prisma studio` відкриє локальну адмінку бази у браузері. Якщо таблиці є — шар БД працює.

### 3. Перевірка фронтенду (шар Next.js)

- **Запуск:** `npm run dev`
- **Перевірка:** Відкриваємо `http://localhost:3000` (якщо порт вільний, за замовчуванням використовується 3000, але оскільки на ньому Gotenberg, Next.js сам запропонує порт 3001). Має відкритися стандартна сторінка Next.js з нашими Tailwind-стилями.

### 4. Перевірка бекенду (API)

Замість складної конвертації пишемо простий Health Check.

- **Дія:** У файлі `app/api/health/route.ts` пишемо функцію `GET`, яка виконує три прості дії:

1. Запитує `prisma.user.count()` (перевірка зв'язку з БД).
2. Виконує `fetch('<http://localhost:3000/health>')` до контейнера Gotenberg.
3. Повертає JSON: `{ db: "ok", gotenberg: "ok" }`.

- **Перевірка:** Викликаємо `http://localhost:3001/api/health` через браузер або REST Client. Якщо повернувся JSON з "ok" — вся наша багатошарова архітектура успішно взаємодіє між собою.

**А це ніяк не перетинається з DESIGN.md, який готував нещодавно? Ініціалізуємо Shadcn UI: `npx shadcn-ui@latest init`. Обираємо стиль (наприклад, New York) і базовий колір (Zinc/Slate).**

Пряма відповідь: **так, тут є невеликий перетин (і потенційний технічний конфлікт).**

Команда ініціалізації `npx shadcn-ui@latest init` створює базовий шаблон, який дещо відрізняється від кастомних налаштувань із вашого `DESIGN.md`. Це цілком нормальна ситуація під час налаштування проєкту, але ці відмінності треба буде вручну узгодити.

Ось основні нюанси та способи їх вирішити:

## 1. Найменування CSS-змінних (токени)

- **Що робить Shadcn:** Під час ініціалізації він генерує файл `globals.css` зі своїми стандартними змінними Tailwind (наприклад, `-background`, `-foreground`, `-primary`, `-muted`).
- **Що в DESIGN.md:** Ваш дизайн-документ використовує власну семантику токенів: `-color-background`, `-color-text-primary`, `-color-accent`, `-space-2`.
- **Рішення:** Вам (або вашому AI-асистенту) потрібно буде зайти до `tailwind.config.ts` і перепризначити стандартні класи Tailwind на ваші змінні. Наприклад, колір `primary` у конфігурації Tailwind треба буде пов'язати з `var(--color-accent)` із `DESIGN.md`.

## 2. Базові кольори (Zinc/Slate vs. хардкод)

- **Що робить Shadcn:** Вибір базового кольору "Zinc" або "Slate" у CLI автоматично пропише відтінки з палітри Tailwind у `globals.css`.
- **Що в DESIGN.md:** Документ задає конкретні hex-коди. Наприклад, `-color-text-primary: #1F2937` (це ближче до відтінку Gray-800) і `-color-border: #E5E7EB` (Gray-200).
- **Рішення:** Після роботи CLI-утиліти Shadcn потрібно буде просто скопіювати блок `:root` із секції **Quick Start** вашого `DESIGN.md` і вставити його поверх того, що згенерував Shadcn, щоб інтерфейс відповідав вашому стандарту.

## 3. Заокруглення (Border Radius)

- **Що робить Shadcn:** Стиль "New York" за замовчуванням використовує менші заокруглення (зазвичай `0.3rem` або `0.5rem`) і менший шрифт.
- **Що в DESIGN.md:** У документі жорстко зафіксовані значення: `6px` для кнопок та інпутів, а також `8px` для карток.
- **Рішення:** У згенерованому `globals.css` потрібно буде оновити глобальну змінну `-radius`, щоб вона відповідала вашим `6px` і `8px`.

Іще один нюанс хотів обговорити. Бачу, що після останніх оновлень VS Code і Gemini Code Assist перестали працювати MCP-сервери для агента Gemini. Спробував: тепер нормально можна працювати лише через Gemini CLI, але там не можна створювати / змінювати файли. Є варіант через MCP GitHub/GitLab, а потім підтягувати все у VS Code. А агентом уже робити локальні правки.
Це якось впливає на наші плани?

Це класична історія з bleeding-edge інструментами — оновлення часто ламають крихкі інтеграції на кшталт локальних MCP-серверів.

На наші глобальні плани щодо архітектури та запуску Convertly Hub це **жодним чином не впливає**. Змінюється лише механіка того, чиїми "руками" створюватимуться файли на диску. Твій варіант із віддаленим репозиторієм — це не просто робочий обхідний шлях, а чудовий зрілий підхід. Звична зв'язка з локального VS Code, Docker-контейнеризації та GitLab Web IDE ідеально лягає на цей воркфлоу, перетворюючи тимчасовий баг MCP на привід одразу побудувати коректний GitOps-процес.

Ось як можна адаптувати інструкцію до цих реалій, щоб не втрачати темп:

## Як тепер виглядає робочий процес

- **Етап 1: Ручний локальний старт.** Ініціалізацію порожнього проєкту (команди `create-next-app`, `shadcn-ui init`, `prisma init`) і створення файлу `docker-compose.yml` ти виконуєш локально в терміналі VS Code. Це безпечні шаблонні дії, для яких AI-агент із генерації файлів не потрібен.
- **Етап 2: Фіксація та push.** Створений базовий каркас проєкту одразу комітиш і надсилаєш у віддалений репозиторій (GitHub або GitLab).
- **Етап 3: Віддалена кодогенерація (магія MCP).** Підключивши агента через MCP до репозиторію, передаєш йому наші `DESIGN.md` і ТЗ. Агент пише код (роути, UI-компоненти, логіку Prisma) й оформлює це у вигляді комітів або Merge/Pull Requests просто у вебінтерфейсі.
- **Етап 4: Локальне тестування.** Ти виконуєш `git pull` у своєму VS Code, піднімаєш контейнери через `docker compose up` і перевіряєш, чи все працює на localhost.
- **Етап 5: Точкові правки.** Якщо потрібно щось виправити (з'їхала верстка, помилка в консолі), використовуєш локальний Gemini Code Assist у режимі чату для пошуку рішення, а саму правку коду вносиш вручну.

## Чому це навіть краще для поточної стадії

- **Чиста історія.** Ти завжди бачиш, що саме згенерував AI у межах Pull Request, перш ніж цей код потрапить на локальний диск. Це захищає від ситуацій, коли агент мовчки перезаписує половину потрібних файлів.
- **Безпечна інфраструктура.** Локальний Docker і конфігурації `.env` залишаються під повним ручним контролем, а AI займається виключно кодом бізнес-логіки в репозиторії.

Можемо почати просто зараз за цим сценарієм. Який блок файлів спробуємо згенерувати першим для надсилання до репозиторію — базову схему бази даних для Prisma чи каркас головної сторінки з Drag & Drop віджетами?

## Чи можна пропустити крок із Shadcn UI?

Так, абсолютно. Якщо ти хочеш повністю контролювати верстку й зібрати UI-kit чітко за своїм `DESIGN.md`, пропуск `shadcn-ui init` — чудова ідея.

Під час переходу до повноцінної Full Stack розробки вміння збирати інтерфейс руками без сторонніх UI-обгорток дає велику перевагу, повний контроль над архітектурою та глибоке розуміння роботи React-компонентів.

У Next.js (у парадигмі App Router) папки, назву яких обгорнуто круглими дужками, називаються **Route Groups (групи маршрутів)**. Це спеціальний синтаксис фреймворку, який одразу розв'язує кілька важливих задач:

## 1. Вони не впливають на підсумкову URL-адресу

У Next.js будь-яка звичайна папка всередині `app/` автоматично стає частиною посилання у браузері. Але якщо папка в дужках, фреймворк робить її "невидимою" для роутингу:

- Файл за шляхом `app/(auth)/login/page.tsx` буде доступний за адресою `твій-домен.com/login` (а не `/auth/login`).
- Файл за шляхом `app/(dashboard)/docs/page.tsx` буде доступний за адресою `твій-домен.com/docs`.

## 2. Різні обгортки (Layouts) для різних сторінок

Це головна причина їх використання. У Next.js можна створювати файли `layout.tsx`, що обгортають сторінки (наприклад, додають хедер або футер). Групи маршрутів дозволяють застосувати зовсім різний дизайн до різних частин сайту, не ламаючи загальну структуру:

- Усередині `app/(auth)` можна розмістити свій `layout.tsx`, який рендеритиме сторінки входу та реєстрації на чистому білому тлі по центру екрана (без меню навігації).
- Усередині `app/(dashboard)` можна розмістити інший `layout.tsx`, який автоматично додаватиме до всіх сторінок у цій групі бічну панель (Sidebar), шапку профілю та перевірятиме, чи авторизований користувач.

## 3. Логічна організація

Коли проєкт розростеться, це допоможе не заплутатися. Відкриваєш редактор і одразу бачиш логічні блоки: тут усе для авторизації, тут усе для особистого кабінету, а публічні API-маршрути лежать окремо.

Тож сміливо натискай "New Folder" і вводь назву одразу з дужками: `(auth)` і `(dashboard)`.

## .env

1. **Як працює Next.js:** Він досить розумний і автоматично читає змінні з цілої ієрархії файлів: `.env`, `.env.local`, `.env.development` тощо. Йому байдуже, де лежать змінні — він їх знайде.
2. **Як працює Prisma (CLI):** Натомість утиліти Prisma (коли ти пишеш у терміналі `npx prisma db push` або `npx prisma studio`) за замовчуванням дещо обмежені. Вони шукають рядок підключення до бази даних _строго_ у файлі з назвою `.env`. Якщо перейменувати його на `.env.local`, Prisma просто видасть помилку, що не може знайти `DATABASE_URL` (доведеться щоразу вказувати шлях до файлу вручну через прапорці, що дуже незручно).

**Який індустріальний стандарт для зв'язки Next.js + Prisma:**
Файл лишають із назвою `.env`, щоб Prisma працювала "з коробки", і обов'язково перевіряють, щоб рядок `.env` був доданий до файлу `.gitignore`. Так секрети лишаються тільки на локальному комп'ютері та не потрапляють до репозиторію.

## 1. Шпаргалка: послідовність запуску проєкту

Щоразу, коли сідаєш працювати (наприклад, після перезавантаження комп'ютера), процес має виглядати так:

### Крок 1. Інфраструктура (Docker)

Спочатку запускаємо наші «фонові» сервіси: базу даних, сховище та воркер конвертації.

- **Дія:** Запусти програму Docker Desktop на комп'ютері й дочекайся, поки вона завантажиться.
- **Команда в терміналі (у корені проєкту):**

```bash
docker compose up -d
```

_(Прапорець `-d` означає detached — контейнери запустяться у фоні та звільнять термінал)._

### Крок 2. Синхронізація бази (Prisma) — _необов'язково_

Ці команди потрібні **лише** якщо ти вносив зміни до файлу `schema.prisma` (наприклад, додав нове поле або таблицю) або завантажив проєкт на новий комп'ютер. Якщо схему не чіпав, цей крок пропускаємо.

- **Застосувати зміни до БД:**

```bash
npx prisma db push
```

- **Оновити типи TypeScript:**

```bash
npx prisma generate
```

### Крок 3. Запуск застосунку (Next.js)

Коли база й сервіси готові, запускаємо сам фреймворк.

- **Команда:**

```bash
npm run dev
```

_(Після цього проєкт доступний у браузері, зазвичай на `http://localhost:3000` або `3001`)._

### 🛑 Як усе зупинити

Коли закінчуєш роботу, у терміналі, де працює `npm run dev`, натисни **`Ctrl + C`**. Щоб зупинити фонові контейнери Docker (щоб не споживали оперативну пам'ять), виконай:

```bash

```

## 2. Як додавати дані до бази

Є два основні способи роботи з даними: ручний (для тестів) і програмний (для реальної роботи застосунку).

### Спосіб А: візуально (через Prisma Studio)

Це найпростіший спосіб перевірки. Він ідеально підходить, щоб швидко додати тестового користувача або переглянути, чи зберігся лог.

1. Виконай у терміналі:

```bash
npx prisma studio
```

1. Відкриється вкладка у браузері.
2. Натисни на таблицю `User`.
3. Натисни кнопку **"Add record"** (додати запис).
4. Заповни поля (наприклад, введи email і будь-який пароль; `id`, `createdAt` та `updatedAt` заповняться самі).
5. Натисни зелену кнопку **"Save 1 change"** вгорі. Дані у базі!

### Спосіб Б: програмно (через код TypeScript)

Саме так працюватиме твій Convertly Hub. Коли користувач реєструватиметься на сайті, твій API-маршрут виконає приблизно такий код.

Ось приклад того, як це виглядає на практиці (можеш зберегти цей сніпет на майбутнє):

```tsx
import { PrismaClient } from "@prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const adapter = new PrismaPg(pool);
const prisma = new PrismaClient({ adapter });

async function createTestUser() {
  // Викликаємо метод create у моделі user
  const newUser = await prisma.user.create({
    data: {
      email: "test@example.com",
      password: "hashed_password_here", // Насправді пароль потрібно хешувати!
    },
  });

  console.log("Створено користувача:", newUser);
}
```

Для таблиць, які пов'язані між собою (як `User` і `ConversionLog`), можна буде створювати записи разом або прив'язувати лог конвертації до конкретного `id` користувача.

База даних працює **всередині контейнера** (`convertly_db`), але хвилюватися за збереження даних під час перезапуску **не потрібно** — вони не зникнуть.

Ось як це влаштовано "під капотом":

1. **Контейнер ≠ дані:** Сам контейнер із базою даних — це лише ізольоване середовище виконання. Якщо його видалити або зупинити (`docker compose down`), сам контейнер буде стерто.
2. **Docker Volumes (томи):** Для надійності в нашому `docker-compose.yml` прописано спеціальний механізм постійного зберігання — volume із назвою `db_data`:

```yaml
volumes:
  db_data:
```

Цей том мапиться (прив'язується) до внутрішньої папки PostgreSQL, де фізично лежать файли бази даних (`/var/lib/postgresql/data`), але ці файли зберігаються **на хост-машині** (твоєму комп'ютері) окремо від життєвого циклу контейнера.

## Що відбувається за різних дій:

- **`docker compose stop`** (або зупинка Docker Desktop): Контейнери просто засинають. Дані повністю на місці.
- **`docker compose down`**: Контейнери видаляються, але **volume `db_data` зберігається**. Коли знову введеш `docker compose up -d`, контейнер запуститься та підхопить усі старі таблиці й записи.
- **`docker compose down -v`** (із прапорцем `v`): Ця дія **видалить і томи** (volumes). Якщо її виконати, усі дані з бази справді буде стерто. У звичайній роботі без гострої потреби цей прапорець використовувати не варто.
