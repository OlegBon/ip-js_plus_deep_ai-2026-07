# Аудит продуктивності Convertly Hub — 2026-08-31

- **UTC-мітка:** 2026-08-31T16:44:57.000Z
- **Оточення:** локальний `next dev` на `localhost:3001`; PostgreSQL, MinIO та
  Gotenberg доступні, що підтверджено `GET /api/health`.
- **Методика:** п'ять послідовних HTTP-вимірювань головної та health-маршруту,
  одна браузерна навігація Playwright і статичний аналіз маршрутів конвертації,
  адміністрування та Prisma-схеми.
- **Обмеження:** це не production-збірка і не Lighthouse/CrUX-вимірювання. Тому
  LCP, INP і CLS не мають достовірних числових значень і не порівнюються з порогами
  Core Web Vitals.

## 2. План дій

1. **[Мережа]** Перед production зібрати застосунок через `next build` + `next start` і
   зняти Lighthouse для головної, Dashboard та Pricing у мобільному профілі. Навіщо:
   отримати справжні LCP, INP і CLS замість показників dev-сервера.
2. **[Сервер]** До підвищення навантаження винести конвертацію у стійку чергу з
   окремим worker-ом, обмеженням паралелізму та пам'яті. Навіщо: не блокувати
   Next.js і уникнути вичерпання пам'яті на великих паралельних завантаженнях.
3. **[БД]** За зростання даних зняти `EXPLAIN ANALYZE` для пошуку та додати
   `pg_trgm`-індекси за `User.email`, `User.name` і назвою вихідного файлу. Навіщо:
   зберегти швидкі живий пошук і пагінацію.
4. **[Клієнт]** За потреби замінити текстове очікування сесії skeleton-інтерфейсом
   або передавати початковий статус із сервера. Навіщо: поліпшити сприйману швидкість
   першого екрана.
5. **[Клієнт / Мережа]** Після production-збірки окремо перевірити, чи зникає
   скасований запит гостьової квоти. Навіщо: не оптимізувати dev-поведінку, якої
   немає у кінцевого користувача.
