# Аудит производительности Convertly Hub — 2026-08-31

- **UTC-метка:** 2026-08-31T16:44:57.000Z
- **Окружение:** локальный `next dev` на `localhost:3001`; PostgreSQL, MinIO и
  Gotenberg доступны, что подтверждено `GET /api/health`.
- **Методика:** пять последовательных HTTP-измерений главной и health-маршрута,
  одна браузерная навигация Playwright и статический анализ маршрутов конвертации,
  администрирования и Prisma-схемы.
- **Ограничение:** это не production-сборка и не Lighthouse/CrUX-измерение. Поэтому
  LCP, INP и CLS не имеют достоверных числовых значений и не сравниваются с порогами
  Core Web Vitals.

## 2. Action Plan

1. **[Сеть]** Перед production собрать приложение через `next build` + `next start` и
   снять Lighthouse для главной, Dashboard и Pricing в мобильном профиле. Зачем:
   получить настоящие LCP, INP и CLS вместо показателей dev-сервера.
2. **[Сервер]** До повышения нагрузки вынести конвертацию в устойчивую очередь с
   отдельным worker-ом, ограничением параллелизма и памяти. Зачем: не блокировать
   Next.js и избежать исчерпания памяти на крупных параллельных загрузках.
3. **[БД]** При росте данных снять `EXPLAIN ANALYZE` для поиска и добавить
   `pg_trgm`-индексы по `User.email`, `User.name` и имени исходного файла. Зачем:
   сохранить быстрые живой поиск и пагинацию.
4. **[Клиент]** При необходимости заменить текстовое ожидание сессии skeleton-интерфейсом
   либо передавать начальный статус с сервера. Зачем: улучшить воспринимаемую скорость
   первого экрана.
5. **[Клиент / Сеть]** После production-сборки отдельно проверить, исчезает ли
   отменённый запрос гостевой квоты. Зачем: не оптимизировать dev-поведение, которого
   нет у конечного пользователя.
