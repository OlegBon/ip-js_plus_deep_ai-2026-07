# Отчет о аудите безопасности (2026-08-09)

## Краткие выводы
Аудит безопасности проекта 'convertly-hub' показывает, что он находится на очень ранней, незавершенной стадии. Однако несколько значительных уязвимостей безопасности уже были внедрены в его базовую конфигурацию.

---

### **[КРИТИЧЕСКИЙ] Целостность зависимостей и риск в цепочке поставок**
- **Расположение:** `package.json`
- **Серьезность:** КРИТИЧЕСКАЯ
- **Описание:** Файл `package.json` ссылается на несколько зависимостей с версиями, которые не существуют в публичном реестре npm (например, `next: '16.3.0'`, `bcrypt: '6.0.0'`). Это подразумевает использование пакетов из неизвестного, частного или потенциально скомпрометированного источника.
- **Риск:** Это создает серьезный риск атак на цепочку поставок, таких как "dependency confusion" или использование вредоносного/непроверенного кода, что может скомпрометировать все приложение и его данные.
- **Рекомендация:** Немедленно исследовать происхождение этих пакетов. Убедиться, что все зависимости поступают из официального, доверенного реестра npm. Обновить все версии до известных, безопасных выпусков. Если используется частный реестр, убедиться в его безопасности и целостности.

---

### **[ВЫСОКИЙ] Жестко закодированные слабые учетные данные**
- **Расположение:** `docker-compose.yml`
- **Серьезность:** ВЫСОКАЯ
- **Описание:** Файл `docker-compose.yml` содержит жестко закодированные, стандартные и слабые учетные данные для базы данных PostgreSQL (`POSTGRES_PASSWORD: 'postgres_password'`) и сервиса хранения объектов Minio (`MINIO_ROOT_PASSWORD: 'minioadminpassword'`).
- **Риск:** Включение секретов в исходный код делает их доступными для всех, кто имеет доступ к репозиторию. Слабые, стандартные учетные данные легко угадать, что делает базу данных и файловое хранилище уязвимыми для несанкционированного доступа, кражи данных или их уничтожения.
- **Рекомендация:** Удалить все жестко закодированные секреты. Перенести их во внешние переменные окружения, загружаемые из файла `.env`. Файл `.env` должен быть добавлен в `.gitignore` и управляться безопасно. Использовать сильные, случайно сгенерированные пароли для всех сервисов.

---

### **[СРЕДНИЙ] Небезопасное сетевое обнаружение**
- **Расположение:** `docker-compose.yml`
- **Серьезность:** СРЕДНЯЯ
- **Описание:** Сервисы `db` (PostgreSQL) и `minio` открывают свои порты по умолчанию (`5432:5432`, `9000:9000`, `9001:9001`) для сетевого интерфейса хост-машины.
- **Риск:** В производственной или общей среде это может открыть базу данных и хранилище объектов напрямую для локальной сети или даже интернета, если правила брандмауэра не настроены должным образом, обходя уровень приложения для доступа.
- **Рекомендация:** Не открывать порты сервисов для хоста, если это не является абсолютно необходимым для отладки. Для межконтейнерной связи полагаться на внутреннюю сеть Docker. Если требуется внешний доступ, ограничить его до доверенных IP-адресов на уровне брандмауэра.

---

### **[СРЕДНИЙ] Отсутствие заголовков безопасности HTTP**
- **Расположение:** `next.config.ts`
- **Серьезность:** СРЕДНЯЯ
- **Описание:** Конфигурация Next.js минимальна и не реализует необходимые заголовки безопасности HTTP.
- **Риск:** Отсутствие заголовков, таких как `Content-Security-Policy` (CSP), `Strict-Transport-Security` (HSTS), `X-Frame-Options` и `X-Content-Type-Options`, делает приложение более уязвимым для ряда атак, включая межсайтовый скриптинг (XSS), кликджекинг и "content sniffing".
- **Рекомендация:** Настроить комплексную политику заголовков безопасности в `next.config.ts` для обеспечения защиты на уровне браузера.

---

### **[ИНФОРМАЦИОННЫЙ] Незавершенная логика аутентификации и API**
- **Расположение:** `app/(auth)/`, `app/api/v1/`
- **Серьезность:** ИНФОРМАЦИОННАЯ
- **Описание:** Каталоги и файлы для аутентификации (`login`, `register`) и конечных точек API в настоящее время являются пустыми заполнителями.
- **Рекомендация:** По мере развития эти области должны стать основным фокусом для обеспечения безопасности. Реализовать надежную проверку вводимых данных, безопасное хеширование и хранение паролей (например, с использованием `bcrypt`), правильное управление сеансами и принцип наименьших привилегий для проверок авторизации на всех конечных точках API.

---

### **[ИНФОРМАЦИОННЫЙ] Поле пароля в схеме**
- **Расположение:** `prisma/schema.prisma`
- **Серьезность:** ИНФОРМАЦИОННАЯ
- **Описание:** Модель `User` правильно содержит поле `password`.
- **Рекомендация:** Это подчеркивает необходимость убедиться, что логика приложения, когда она будет реализована, НИКОГДА не будет хранить пароли в открытом виде в базе данных. Значение, хранящееся в этом поле, должно быть сильным, соленым хешем, сгенерированным библиотекой типа `bcrypt`.

---

### **[СРЕДНИЙ] Неправильное управление подключением к базе данных**
- **Расположение:** `app/api/health/route.ts`
- **Серьезность:** СРЕДНЯЯ
- **Описание:** Соединение с базой данных создается непосредственно в обработчике маршрута. Это не является хорошей практикой.
- **Риск:** Создание нового соединения при каждом вызове может привести к исчерпанию лимита подключений к базе данных при высокой нагрузке, что приведет к отказу в обслуживании.
- **Рекомендация:** Создать единый экземпляр клиента Prisma и использовать его повторно во всем приложении.

---

### **[НИЗКИЙ] Незначительная утечка информации в эндпоинте Health Check**
- **Расположение:** `app/api/health/route.ts`
- **Серьезность:** НИЗКАЯ
- **Описание:** Эндпоинт проверки состояния возвращает количество пользователей в базе данных (`userCount`).
- **Риск:** Это может рассматриваться как незначительная утечка информации. Раскрытие количества пользователей может быть использовано для анализа активности платформы.
- **Рекомендация:** Вместо фактического количества пользователей возвращать общее сообщение "database connected".

---

### **[ИНФОРМАЦИОННЫЙ] Раскрытие внутреннего сервиса**
- **Расположение:** `app/api/health/route.ts`
- **Серьезность:** ИНФОРМАЦИОННАЯ
- **Описание:** Эндпоинт проверки состояния показывает, что внутренний сервис `gotenberg` работает на `http://localhost:3000`.
- **Риск:** Это не является уязвимостью само по себе, но это ценная информация для злоумышленника, который может попытаться найти уязвимости в этом сервисе.
- **Рекомендация:** Логировать ошибки внутренних сервисов, но не раскрывать их в ответах API.
