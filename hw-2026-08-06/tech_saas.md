# ⚙️ Convertly Hub - SaaS File Converter & API Platform

Мікросервіс для швидкої конвертації файлів із наданням публічного API для розробників. Проєкт поєднує зручний користувацький інтерфейс і надійну серверну інфраструктуру обробки даних.

---

## 1. Вступ і цілі проєкту

**Назва проєкту (робоча):** Convertly Hub

**Основна суть продукту:**
Проєкт є вебзастосунком (SaaS-платформою), що надає послуги швидкої конвертації файлів між різними форматами. Взаємодія із сервісом відбувається двома шляхами: через графічний користувацький інтерфейс (B2C-сценарій для звичайних користувачів) і через публічне REST API (B2B/Developer-сценарій для інтеграції зі сторонніми програмними продуктами).

**Основна ціль:**
Розробити легковаговий, але архітектурно масштабований сервіс конвертації файлів, що містить повноцінну систему авторизації, керування профілем користувача, генерацію унікальних ключів доступу й надійне ядро (Core) для обробки медіафайлів і документів.

**Ключові завдання проєкту:**

1. **Реалізація Core-частини.** Створення відмовостійкого механізму приймання, обробки та повернення файлів без критичного навантаження на основний сервер.
2. **Надання API.** Розроблення захищеного ендпойнта, який дасть стороннім розробникам змогу надсилати файли на конвертацію, використовуючи унікальний API-ключ.
3. **Керування станом користувача.** Створення особистого кабінету з гнучкими налаштуваннями приватності (можливістю вмикати/вимикати зберігання сконвертованих файлів на сервері).
4. **Побудова UX/UI.** Розроблення інтуїтивно зрозумілого інтерфейсу для ручного завантаження файлів із коректним зворотним зв’язком за будь-яких сценаріїв (успіх, помилка, перевищення ліміту).

## 2. Архітектура й технологічний стек

### 2.1. Концепція архітектури

Система будується за принципом розподілу відповідальності (Separation of Concerns) і концептуально ділиться на три незалежні шари. Такий підхід забезпечує відмовостійкість, характерну для надійних корпоративних сервісів, і дає змогу масштабувати кожен компонент окремо:

- **Клієнтська частина (Frontend).** Вітрина сервісу та інтерактивний особистий кабінет користувача.
- **Серверна частина й API (Backend).** Обробка бізнес-логіки, автентифікація, маршрутизація та перевірка лімітів.
- **Core-рушій (Workers).** Ізольоване середовище для виконання ресурсомістких завдань із перекодування файлів.

### 2.2. Основний фреймворк та інтерфейс

- **Фреймворк: Next.js (App Router).** Виконує роль головного оркестратора. Використовується для серверного рендерингу (SSR) інтерфейсу та створення захищених API-маршрутів.
- **Стилізація та UI: Tailwind CSS.** Забезпечує створення строгих, легковагових і повторно використовуваних UI-компонентів без перевантаження клієнтської частини зайвими CSS-бібліотеками. Особлива увага приділяється візуальному зворотному зв’язку: мікровзаємодіям, станам зон Drag & Drop й індикаторам прогресу.

### 2.3. Інфраструктура даних

- **Реляційна база даних.** PostgreSQL у зв’язці з Prisma ORM. Відповідає за надійне зберігання строго структурованих транзакційних даних: профілів користувачів, хешів паролів, згенерованих API-ключів і логів (історії) конвертацій. Самі файли в БД не зберігаються.
- **Об’єктне сховище.** S3-сумісне сховище (наприклад, MinIO або AWS S3). Забезпечує потокове завантаження (Streaming) і віддавання файлів. Використання незалежного сховища закладає архітектурний потенціал для горизонтального масштабування та керування великими обсягами медіаданих (аж до виділення терабайтних пулів під обліковий запис).

> **Уточнення щодо інфраструктури сховища:**
> Для MVP, захисту проєкту й навіть початкового запуску SaaS-продукту на старті не доведеться платити за сховище. Архітектура S3 стала стандартом (API), тому є кілька чудових безкоштовних варіантів реалізації:
>
> - **MinIO (локально для розробки).** Це S3-сумісне сховище, яке локально запускається через Docker буквально однією командою. Воно не потребує інтернету й фінансових витрат. Ідеально для написання коду та тестування. Коли код працює з MinIO, він працюватиме з будь-яким іншим S3-сховищем без переписування логіки.
> - **Cloudflare R2 (для продакшену).** Безкоштовний тариф щомісяця надає 10 ГБ сховища й нульову вартість вихідного трафіку (egress fees). Для SaaS-конвертера, де користувачі постійно завантажують файли, це оптимальний вибір.
> - **AWS S3 Free Tier.** Amazon надає 5 ГБ безкоштовно на перші 12 місяців.
> - **Supabase Storage.** Під час використання Supabase як бази даних (PostgreSQL) платформа надає вбудоване S3-сховище (1 ГБ у безкоштовному тарифі).
>
> _Отже, проєкт Convertly Hub може бути повністю реалізований і запущений на базі безкоштовних потужностей._

### 2.4. Core-рушій та ізоляція процесів (вирішення проблеми Event Loop)

Оскільки JavaScript є однопотоковою мовою, виконання складних математичних обчислень безпосередньо на сервері бекенду неминуче призведе до блокування Event Loop. Щоб «важкий» файл не зупинив роботу всього сервісу для інших клієнтів, застосовується розділений підхід:

- **Синхронна обробка (легкі завдання).** Конвертація зображень (`JPG ↔ PNG`) виконується за допомогою високопродуктивної бібліотеки `sharp` (Node.js). Операція відбувається на рівні C++, займає мілісекунди й безпечно виконується в основному процесі.
- **Ізольована обробка (важкі завдання).** Конвертація документів (`DOCX → PDF`) делегується окремому мікросервісу (наприклад, `Gotenberg`, розгорнутому в ізольованому Docker-контейнері). Next.js тут виступає винятково шлюзом: приймає файл потоком, передає його мережею незалежному воркеру, очікує на відповідь і повертає готовий PDF клієнту. Це гарантує безперебійну роботу основного API та UI навіть за пікового навантаження.

## 3. Вибір форматів файлів і бізнес-логіка

### 3.1. Підтримувані формати (Scope для MVP)

У межах першої версії продукту реалізовано підтримку двох найзатребуваніших напрямів конвертації, кожен із яких демонструє різні архітектурні підходи до обробки даних:

- **Зображення (JPG ↔ PNG).** Демонструє миттєву (синхронну) обробку легковагових медіафайлів. Виконується потоково, не потребує значних ресурсів і дає змогу протестувати пропускну здатність API за численних запитів.
- **Документи (DOCX → PDF).** Демонструє асинхронну обробку та роботу Core-рушія з важкими форматами. Має високу комерційну цінність (B2B-сегмент) і доводить здатність архітектури не блокувати основний Event Loop сервера під час складних математичних операцій рендерингу шрифтів і розмітки.

### 3.2. Політика зберігання та керування приватністю (User Control)

Ядром бізнес-логіки платформи є суворий контроль користувача над своїми даними. Керування здійснюється через глобальний перемикач (Toggle) «Зберігати результати конвертації», розташований в особистому кабінеті.

Логіка роботи механізму:

- **Стан «Активно» (за замовчуванням).** Усі завантажені файли (як через вебінтерфейс, так і через публічне API) після успішної конвертації зберігаються в S3-сховищі. У базі даних створюється запис із метаданими файлу, який одразу відображається в таблиці файлового менеджера в особистому кабінеті користувача.
- **Стан «Вимкнено» (Privacy Mode).** Система переходить у режим обробки «на льоту» (In-Memory / Temp Storage). Сконвертований файл повертається клієнту як бінарний потік або тимчасове захищене посилання (TTL 1 година) і негайно видаляється із серверів платформи.
- **Ізоляція станів (зворотна сумісність).** Переведення перемикача в неактивне положення впливає винятково на майбутні конвертації. Файли, які вже є у профілі користувача, не піддаються автоматичному видаленню й лишаються доступними для завантаження до ручного видалення користувачем.

## 4. Структура сторінок і користувацькі сценарії (UI/UX)

### 4.1. Головна сторінка (Landing & Conversion Zone)

- **URL:** `/`
- **Призначення:** Основна точка входу, що демонструє ключову цінність сервісу без обов’язкової реєстрації.
- **Структура блоків:** Hero-секція з описом і два віджети Drag & Drop (зона завантаження зображень і зона завантаження документів). Індикатор прогресу конвертації та кнопка завантаження.

### 4.2. Блок авторизації (Auth Flow)

- **URL:** `/auth/login` и `/auth/register`
- **Призначення:** Ідентифікація користувачів для доступу до функціоналу особистого кабінету.
- **Структура блоків:** Мінімалістичні форми з полями Email і Password, а також посиланнями на відновлення доступу.

### 4.3. Особистий кабінет (Dashboard & Profile Management)

- **URL:** `/dashboard` (доступно лише авторизованим користувачам)
- **Призначення:** Центр керування обліковим записом.
- **Структура блоків:**
  - **Керування профілем:** Редагування особистих даних.
  - **Керування API-доступом:** Блок із поточним API-ключем, кнопками копіювання та повторної генерації.
  - **Налаштування сховища:** Перемикач «Зберігати сконвертовані файли у профілі».
  - **Файловий менеджер:** Таблиця з історією транзакцій і посиланнями для завантаження збережених файлів.

### 4.4. Сторінка документації API

- **URL:** `/docs`
- **Призначення:** Технічний посібник для сторонніх розробників з інтеграції конвертера.
- **Структура блоків:** Опис ендпойнтів, вимоги до автентифікації (Bearer-токен), сніпети коду (cURL, JS) і таблиця розшифрування HTTP-помилок.

### 4.5. Панель адміністратора (Admin Panel)

- **URL:** Прихований ендпойнт (наприклад, `/system-manage/login` або `/portal-access`). Суворо виключений із файла `robots.txt` і карти сайту.
- **Призначення:** Внутрішній інструмент для керування платформою та моніторингу її стану.
- **Структура блоків:**
  - **Дашборд метрик:** Загальна кількість користувачів, кількість конвертацій за 24 години, навантаження на воркери.
  - **Керування користувачами:** Пошук за Email, можливість примусового блокування облікового запису (Banned) або ручного скидання пароля.
  - **Керування API-ключами:** Можливість відкликання (Revoke) ключів, для яких зафіксовано аномальне навантаження або спам-активність.

## 5. Авторизація та керування доступом

### 5.1. Основний механізм автентифікації

Для забезпечення безпеки сесій і роботи публічного API використовується комбінований підхід:

- **Вебклієнт (особистий кабінет).** Автентифікація реалізується на базі бібліотеки `NextAuth.js` (`Auth.js`) із застосуванням захищених `HttpOnly` cookie. Це стандартний і найбезпечніший метод для Next.js-застосунків, що захищає токени сесії від XSS-атак (міжсайтового скриптингу).
- **Публічне API.** Автентифікація відбувається за статичним API-ключем (Bearer Token), який передається в заголовку запиту.

### 5.2. Політика зберігання облікових даних

- Платформа не зберігає паролі користувачів у відкритому вигляді. Під час реєстрації пароль хешується за допомогою криптографічно стійкого алгоритму (наприклад, `bcrypt` або `argon2`) з додаванням унікальної «солі» (salt).
- API-ключі в базі даних також зберігаються як хеші (як паролі). Користувач бачить свій API-ключ повністю лише один раз — у момент генерації. Надалі в інтерфейсі відображаються тільки перші та останні символи (наприклад, `sk_live_...a7f2`).

### 5.3. Захист ендпойнтів авторизації

- Маршрути `/auth/login` і `/auth/register` захищені вбудованим механізмом обмеження кількості запитів (Rate Limiting).
- У разі серії невдалих спроб введення пароля (наприклад, понад 5 разів за хвилину) IP-адреса тимчасово блокується, що запобігає атакам типу Brute Force.

### 5.4. Інноваційний механізм відновлення доступу (Telegram Fallback)

Замість класичного (і часто нестабільного) надсилання листів із кодами підтвердження на email система використовує гібридний підхід для відновлення втраченого пароля, інтегруючи Telegram:

- **Прив’язування облікового запису.** В особистому кабінеті користувач може за бажанням прив’язати свій Telegram-акаунт до профілю Convertly Hub через спеціального бота.
- **Сценарій відновлення.** Натиснувши «Забули пароль?» на сторінці `/auth/login`, користувач вводить свій Email.
- **Доставлення ключа.** Якщо до профілю прив’язано Telegram, система генерує криптографічно стійкий одноразовий токен (Magic Link) зі строком дії 15 хвилин. Telegram-бот одразу надсилає це посилання користувачу.
- **Безпека методу.** Перехід за посиланням із месенджера відразу авторизує користувача й переводить його на захищену сторінку скидання пароля. Це усуває ризик перехоплення email-трафіку та істотно пришвидшує відновлення доступу.

## 6. Механізм роботи публічного API

### 6.1. Архітектура ендпойнтів

Взаємодія з Core-рушієм платформи для сторонніх застосунків відбувається через єдиний захищений маршрут:

- **Метод и URL:** `POST /api/v1/convert`

### 6.2. Автентифікація API-запитів

- Кожен запит до ендпойнта має містити HTTP-заголовок авторизації: `Authorization: Bearer <API_KEY>`.
- За відсутності заголовка, передавання порожнього значення або невідповідності хешу ключа базі даних сервер припиняє обробку й негайно повертає HTTP-статус `401 Unauthorized`.

### 6.3. Формат вхідних даних (Request)

Оскільки API працює з файлами, стандартний формат JSON не застосовується для тіла запиту.

- **Content-Type:** Обов’язково `multipart/form-data`.
- **Тіло запиту (Payload) містить:**
  - `file`: Сам бінарний файл (вихідний файл).
  - `targetFormat`: Рядковий параметр, що вказує бажаний формат на виході (наприклад, `png` або `pdf`).

### 6.4. Формат вихідних даних (Response)

Відповідь сервера динамічно змінюється залежно від налаштувань приватності користувача (положення перемикача в дашборді), якому належить API-ключ:

- **Сценарій «Зберігання увімкнено»:** Сервер повертає статус `200 OK` і JSON-об’єкт, що містить метадані файлу та постійне посилання для його завантаження із S3-сховища.
- **Сценарій «Privacy Mode (без зберігання)»:** Сервер повертає статус `200 OK`, а в тілі відповіді віддає безпосередньо бінарний потік (`Buffer/Stream`) сконвертованого файлу. У заголовках відповіді зазначається `Content-Disposition: attachment; filename="result.pdf"`, що дає клієнтському застосунку змогу відразу почати завантаження.

### 6.5. Керування навантаженням (Rate Limiting)

Для запобігання DDoS-атакам і зловживанню ресурсами воркерів на рівні API реалізовано тротлінг:

- Установлюється жорсткий ліміт (наприклад, 30 запитів на хвилину для одного API-ключа).
- У разі перевищення ліміту сервер не приймає файл на обробку та повертає HTTP-статус `429 Too Many Requests` із заголовком `Retry-After`, що вказує, через скільки секунд можна повторити запит.

## 7. Обробка непередбачених ситуацій (Edge Cases)

Оскільки SaaS-платформа приймає файли від зовнішніх користувачів, вона має бути максимально відмовостійкою та захищеною від зловмисних або помилкових дій. У системі реалізовано багаторівневу обробку винятків:

### 7.1. Перевищення допустимого розміру файлу

- **Клієнтська валідація.** У разі спроби перетягнути файл, що перевищує ліміт (наприклад, > 10 МБ), зона Drag & Drop одразу підсвічується червоним, завантаження блокується, а користувач бачить Toast-сповіщення. Трафік не витрачається.
- **Серверна валідація.** Якщо зловмисник обходить клієнтську перевірку (наприклад, надсилаючи великий файл напряму через cURL до API), бекенд перехоплює розмір потоку. Завантаження примусово переривається, а сервер повертає статус `413 Payload Too Large`.

### 7.2. Підміна формату (MIME-type spoofing)

- Система не довіряє розширенню файлу, переданому клієнтом (наприклад, `document.docx`). Зловмисник може перейменувати виконуваний скрипт `.sh` або вірус `.exe` на `.docx`.
- Сервер аналізує «магічні байти» (file signatures) у заголовку завантаженого файлу. Якщо реальний MIME-тип не збігається із заявленим або не входить до білого списку дозволених форматів, сервер негайно видаляє файл із пам’яті та повертає `415 Unsupported Media Type`.

### 7.3. Збої Core-рушія та пошкоджені файли

- Якщо користувач завантажує пошкоджений або зашифрований паролем `.docx` файл, воркер (`Gotenberg`), який намагається його відкрити, може видати критичну помилку.
- Завдяки ізоляції процесів падіння воркера не призводить до падіння (Crash) основного сервера Next.js. Бекенд перехоплює цю помилку (через блок `try/catch`) і коректно передає клієнту статус `422 Unprocessable Entity` із поясненням: «Неможливо обробити файл. Переконайтеся, що архів не пошкоджено».

### 7.4. Мережеві таймаути

- У разі пікового навантаження, коли черга на конвертацію важких PDF-документів переповнена, запит може зависнути.
- На рівні API встановлено жорсткий таймаут (наприклад, 30 секунд). Якщо воркер не встиг віддати результат, сервер перериває з’єднання, очищає виділену пам’ять і повертає статус `504 Gateway Timeout`, пропонуючи повторити спробу пізніше.

## 8. Візуальні референси

З огляду на відсутність готових Figma-макетів, розроблення інтерфейсу, імовірно, вестиметься за принципом Component-Driven Development із використанням бібліотеки готових UI-рішень.

### 8.1. Дизайн-система та стилістика

- Як основу використовується **Shadcn UI + Tailwind CSS**. Це забезпечить строгий, сучасний і консистентний вигляд без потреби відмальовувати кожен піксель із нуля.
- **Загальний стиль.** Мінімалізм, рясне використання негативного простору (whitespace), чітка типографіка. Колірна палітра монохромна (чорно-біла) з одним акцентним кольором (наприклад, глибоким синім або фіолетовим) для виділення активних станів.

### 8.2. Референси для ключових сторінок

- **Головна сторінка (конвертер).** Візуальним орієнтиром слугує сервіс **iLovePDF**. Зона завантаження файлів має посідати центральне місце. Основний акцент робиться на станах Drag & Drop: нейтральному, наведенні (Hover/Drag Over зі зміною кольору пунктирної рамки), процесі завантаження (анімований прогрес-бар) й успішному завершенні.
- **Особистий кабінет (Dashboard).** Орієнтиром виступають інтерфейси **Vercel** або **Stripe**. Бічна панель навігації (Sidebar), строгі картки налаштувань, перемикачі (Toggles) для зміни режимів і охайні таблиці даних з історією конвертацій.
- **Документація API.** Орієнтир — **Tailwind UI Docs** або **Stripe API Reference**. Обов’язкове використання темної теми для блоків із кодом (Syntax Highlighting) і чітке верстання таблиць із параметрами запитів, щоб документація виглядала як професійний продукт для розробників.
