# Локальные правила: Архитектура

## 1. Архитектура и работа с сервером (Next.js App Router)

- **Стек:** Проект использует Next.js (App Router). Используй **серверные компоненты (Server Components)** по умолчанию для фетчинга данных и снижения размера клиентского бандла. Клиентские компоненты (`"use client"`) применяй только для интерактивных элементов.
- **Асинхронность:** Применяй современные асинхронные паттерны (`async/await`) для работы с API, особенно при получении данных в серверных компонентах.
- **Обработка состояний:** Обязательно реализуй обработку состояний загрузки и ошибок с помощью встроенных файлов Next.js:
    - `loading.tsx` для отображения спиннеров или скелетонов.
    - `error.tsx` для перехвата ошибок и отображения запасного UI.
- **Стилизация:** Используй исключительно утилитарные классы **Tailwind CSS**. Запрещено раздувать глобальные CSS-файлы. Выноси переиспользуемые UI-паттерны в отдельные React-компоненты.

## 2. Паттерны компонентов

- **Container / Presentational:** Разделяй компоненты на "контейнеры", которые отвечают за загрузку данных и логику, и "презентационные", которые только получают пропсы и отображают UI. Это упрощает переиспользование и тестирование.
- **Композиция > Наследование:** Всегда предпочитай композицию. Используй `children` для вставки контента и рендер-пропсы для передачи логики рендеринга.
- **Составные компоненты (Compound Components):** Для сложных виджетов (табы, аккордеоны) используй составные компоненты, которые делят состояние через React Context.

## 3. Управление состоянием (State Management)

Выбирай место для хранения состояния по следующему принципу:

1.  **Локальное состояние (`useState`):** Если данные используются только одним компонентом.
2.  **Поднятие состояния (Lifting State Up):** Если данные нужны нескольким дочерним компонентам, подними состояние до их ближайшего общего родителя.
3.  **Контекст (React Context):** Для глобальных данных, которые читаются во многих местах, но **редко обновляются** (тема, авторизация, локализация).
4.  **Внешнее хранилище (Zustand, Redux):** Для сложного глобального состояния, которое часто обновляется или должно сохраняться между страницами.
5.  **Серверное состояние (TanStack Query, SWR):** Для данных, полученных с сервера (кеширование, мутации, оптимистичные обновления). **Не дублируй серверное состояние в клиентских хранилищах.**

## 4. Получение данных (Data Fetching)

| Стратегия                               | Когда использовать                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| `await fetch` в Серверном Компоненте | Для данных, необходимых при первом рендере страницы. Без клиентского кеширования.        |
| TanStack Query / SWR                    | Для клиентского кеширования, мутаций, оптимистичных обновлений и фоновой ревалидации. |
| `fetch` в `useEffect`                   | **Избегать.** Приводит к гонкам состояний, не имеет кеша и повторных попыток.          |
